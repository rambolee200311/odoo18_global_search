## 2. 背景与动机

验证 BR-009.1、BR-009.2、BR-010、FR-ER-003。GS-03/GS-04 已验证日期范围和条件合并基础语义，但尚未覆盖用户时区、语言周起始日、跨日边界和部分模型失败。

## 3. 验证问题

1. 同维度多值是否为 OR。
2. 多值日期范围是否使用包含起点、排除终点。
3. `今天/本周/本月` 是否按用户时区。
4. 周起始日是否按用户语言。
5. 跨天动态表达是否在同一固定时间点稳定。
6. 部分失败模型是否保留成功模型结果。
7. 部分失败计数是否只统计成功模型。
8. 部分失败是否给出明确模型级提示。
9. 超时是否保留已返回结果并提示。
10. 配置错误是否失败关闭。

## 4. 假设

- 使用隔离数据库 `wd_tv_gs01_20261002_100k`；
- 测试记录通过 Odoo ORM 创建和删除；
- 时间测试使用固定 UTC 时间，避免执行时钟导致结果漂移；
- 当前仓库没有生产 Search Service，因此本 TV 的语义执行器是可复现的 ORM reference harness，不冒充最终服务实现。

## 5. 范围

### In Scope

- `sale.order` ORM 数据；
- 状态 OR、日期范围、时区、语言周起始日；
- 部分失败、超时和配置错误的错误分类/部分成功协议；
- 计数和用户可见提示。

### Out of Scope

- 修改 `odoo/` 或官方 addons；
- 直接 SQL/数据库驱动；
- `sudo()`；
- Elasticsearch、OpenSearch、LLM、向量检索；
- 最终 Global Search UI 和自然语言解析器。

## 6. 方法

1. ORM 创建固定日期、状态和标记的 Sale Orders。
2. 用 ORM domain 验证 OR、日期区间和权限上下文。
3. 用 `fields.Date.context_today` 和已安装语言的 `week_start` 验证时区/周起始日。
4. 用受控异常函数模拟部分失败、超时和配置错误。
5. 保存每个子问题的实际输入、结果、计数和提示。
6. ORM 删除所有 `TV06-` fixture。

## 7. 通过标准

- 同维度多值结果等价于单值结果集合的 OR；
- 日期范围为 `[start, end)`；
- 相同 UTC 时间在不同用户时区产生正确本地日期；
- `en_US` 与 `zh_CN` 使用各自语言周起始日；
- 部分失败不丢弃成功结果，计数不包含失败模型；
- 超时和配置错误均显式提示，配置错误不返回不可信结果。

## 8. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 执行时间跨日 | 固定 UTC timestamp |
| 语言未安装 | 记录实际安装语言并把场景标为未验证 |
| Sale Order 创建副作用 | 仅使用 ORM、固定标记、执行后清理 |
| Reference harness 与产品服务不同 | 报告明确区分语义事实和生产实现状态 |
