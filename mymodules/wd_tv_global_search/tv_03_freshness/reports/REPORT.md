## 2. 摘要

### 核心结论

> **业务记录新鲜度有条件通过；配置新鲜度未验证。**

在隔离数据库中，使用 Odoo ORM 完成单条创建、更新、删除，100 条批量操作和 20 并发读取。每次提交后均使用新的 ORM cursor/environment 执行搜索，避免同一事务缓存造成假阳性。

业务记录结果全部在 5 秒初始目标内可见或失效：

- 创建 P95：0.661 ms；
- 更新 P95：1.045 ms；
- 删除 P95：0.604 ms；
- 批量创建/更新/删除：0.487/0.582/1.025 ms；
- 并发读取错误率：0%，P95：239.615 ms。

但当前 `mymodules/wd_global_search` 目录为空，未发现已安装的配置模型、发布方法或可调用的 Global Search 服务。因此配置发布和停用无法验证，NFR-002 不能整体标记为 VERIFIED。

### 对 SRS V1.4 的影响

- AC-044 业务记录提交后可见的 ORM 基础路径在本环境通过；
- NFR-002 的配置变更立即生效部分仍未验证；
- AC-045、CON-010 需要等配置模型和发布 API 实现后补测；
- V1 范围不调整。

## 4. 方法与执行

### 4.1 实际环境

| 项 | 值 |
|---|---|
| Odoo | 18.0 |
| Python | 3.11.9 |
| CPU | 10 logical cores |
| 数据库 | `wd_tv_gs01_20261002_100k` |
| 数据读写 | Odoo ORM |
| 搜索读取 | 新 ORM cursor/environment |
| `sudo()` | 未使用 |
| 直接数据库业务读写 | 未使用 |

### 4.2 单条操作

每类操作 20 次：

1. ORM 创建/更新/删除；
2. `env.cr.commit()`；
3. 新 ORM cursor/environment 搜索；
4. 记录 commit 成功到观察结果的纳秒时间差。

更新额外检查新值可见、旧值不可见；删除额外检查记录不再命中。

### 4.3 批量操作

每类批量操作 100 条：

- 批量创建后计数；
- 批量更新后按新值计数；
- 批量删除后按 ref 计数；
- 每一步提交后才开始搜索。

### 4.4 高并发

- 先通过 ORM 提交 20 条记录；
- 20 个线程各使用独立 cursor/environment；
- 并发精确搜索；
- 记录错误率、单请求耗时和可见数量。

### 4.5 与 PLAN 的差异

业务记录测试按计划完成。配置发布/停用未执行，因为当前仓库没有 `wd_global_search` 配置模型、发布方法或可调用搜索入口；该差异已作为未验证结果保留。

## 6. 分析

### 6.1 与通过标准对比

- 单条创建、更新、删除 P95 均远低于 5 秒；
- 批量 100 条操作均在毫秒级完成；
- 20 并发错误率 0%，P95 239.615 ms，低于 5 秒；
- 业务记录提交后使用新 cursor 即可读取最新状态；
- 配置发布和停用没有实现表面，无法判断是否无需重启生效。

### 6.2 与 SRS 的关系

- AC-044 的业务记录路径满足初始目标 5 秒；
- NFR-002 是业务记录和配置变更的组合要求，本次只能覆盖前半部分；
- AC-045/CON-010 需要配置模型、版本发布和运行时读取链路后补测。

### 6.3 未预期发现

1. 创建操作 P99 出现一次 16.459 ms 尾延迟，但仍远低于 5 秒；
2. 并发读取 P50/P95 约 239 ms，明显高于串行新 cursor 读取，说明 cursor/线程建立和并发调度成本需要在真实搜索服务中单独控制；
3. 当前自定义模块目录没有实现代码，因此配置新鲜度不存在可测试对象。

## 7. 结论

| 子问题 | 结论 | 条件 |
|---|---|---|
| 创建可见 | 通过 | 当前 ORM 直读路径 |
| 更新可见 | 通过 | 当前 ORM 直读路径 |
| 删除失效 | 通过 | 当前 ORM 直读路径 |
| 配置发布 | 未验证 | 需要配置模型和发布 API |
| 配置停用 | 未验证 | 需要配置模型和停用 API |
| 批量操作 | 通过 | 100 条样本 |
| 高并发 | 通过 | 20 并发、0% 错误 |

### 整体结论

**有条件通过。**

条件为：

1. 业务记录新鲜度在本测试路径满足初始 5 秒目标；
2. 结果不能替代真正 Global Search 搜索服务的端到端验证；
3. 配置发布/停用必须在配置模型和发布 API 实现后补测；
4. 若实现异步索引或缓存，必须重新测量端到端延迟。

## 8. 对 SRS 的影响

### 已验证

- NFR-002 业务记录部分；
- AC-044 在 ORM 直读基线下满足 5 秒初始目标。

### 需要技术方案调整

- 搜索服务必须定义提交确认点和可见性读取点；
- 配置读取不能只依赖进程启动时缓存；
- 批量和并发搜索需保持提交后的可见性；
- 异步索引若引入，必须记录队列延迟并纳入最终上限。

### 未验证

- NFR-002 配置变更部分；
- AC-045 Vocabulary 配置发布；
- CON-010 配置立即生效；
- 真实前端/HTTP/RPC 搜索端到端新鲜度。

## 9. 对技术方案的影响

| 领域 | 影响 |
|---|---|
| 数据模型 | 配置必须有发布状态、版本和生效时间 |
| 缓存 | 配置缓存必须有显式失效或版本检查 |
| 权限 | 记录可见性仍必须在当前用户 ORM 上下文判断 |
| 写入 | 提交成功是新鲜度计时起点，不应以事务开始时间替代 |
| 搜索 | 新 cursor 测试通过后，真实搜索服务仍需端到端测量 |

## 10. 未解决的问题

1. `wd_global_search` 配置模型和发布接口尚未实现；
2. 配置版本切换是否在多 worker 下立即生效；
3. 真实 HTTP/RPC 搜索请求的端到端延迟；
4. 异步索引、消息队列或缓存引入后的延迟；
5. 高并发批量写入同时发生时的尾延迟；
6. 配置权限和公司隔离下的可见性。
