## 一、执行摘要

### 1.1 冻结决策

正式选择 **Route B：LLM 主导 Office 内容生产 + OpenAI Hosted Code Interpreter 执行 + Odoo 本地治理**。

新架构明确分离两项职责：

- **LLM 内容生产层：**理解用户意图、分析文件、决定内容与修改逻辑、生成及编辑 Office 文件。
- **Odoo 治理层：**授权业务数据读取、管理文件版本、验证结果、处理用户确认、记录审计及交付文件。

不再将本地 Mapping、`repeat_rows`、`cell_edits` 等预定义操作作为通用 Office 内容生产的必经路径。

### 1.2 决策依据

2026 年 11 月 10 日的 TV 已通过真实模型 API 调用证明：

1. LLM 可以读取原始 XLSX 并生成有效 XLSX。
2. 可以根据 Odoo 授权数据填充三条真实联系人。
3. 第二轮能够读取第一轮实际生成的 XLSX。
4. 可以增加地址列，同时保留既有 A～C 列内容。
5. 生成文件通过独立回读检查。
6. 当前 Odoo 的主要集成障碍已经定位。
7. 两轮任务的预估 API 成本处于可接受范围。

上述结论适用于本次简单工作簿验证，不代表复杂 Office 文件已全部通过验收。

### 1.3 决策结论

技术路线决议冻结，不再开展同类路线的重复比较；只有出现本报告列出的实质性重新评审条件时才重开。

下一阶段转入 TDD 架构修订与工程实施。

## 二、决策背景

### 2.1 原架构

现有 Office Engine 的主要内容生产路径为：

```text
用户自然语言指令 → LLM 生成结构化 Mapping/操作 → 本地规则校验 → 本地执行器修改文件 → 文件验证及交付
```

其设计初衷是提高确定性、可审计性和文件操作安全性。

### 2.2 实际问题

连续人工验证暴露出以下问题：

- 内容生产依赖预定义操作能力。
- 模板结构需要满足本地执行器的部分假设。
- 新的用户要求可能超出 Mapping 表达范围。
- 局部规则修复无法证明通用任务能力。
- 单元测试通过与真实用户任务成功之间存在明显差距。
- 简单联系人 Excel 任务曾多次无法完成端到端交付。

其中，表头下没有预先存在的数据行导致 `repeat_rows_not_renderable`，是本地内容生产路线受操作表达约束的典型案例。

这些问题不意味着本地 Python 无法操作 Excel，而是表明：

> 通用内容生产能力不能直接等同于有限操作集合的执行能力。

### 2.3 重新决策的必要性

Office Engine 的产品目标是：

> 用户使用自然语言，要求 AI 创建、填写、修改、扩展和持续编辑 Office 文件，而不必理解内部 Mapping、工作表坐标或执行器规则。

原架构尚未通过这一目标下的实际用户验收，因此有必要调整内容生产的职责边界。

## 三、候选技术路线

| 路线 | 内容生产机制 | 验证情况 | 决策 |
|---|---|---|---|
| A | LLM 直接输入/输出 XLSX 二进制文件，无执行工具 | 完整路线未验证 | 暂不采用 |
| B | LLM 使用 Hosted Code Interpreter 生成、修改 XLSX | 简单工作簿两轮通过 | **选定** |
| C | LLM 输出完整工作簿内容描述，本地通用序列化 | 简单工作簿两轮通过 | 不作为主路线 |
| D | LLM 生成 Python 脚本，本地隔离执行 | 未开展同等 TV | 保留备选 |
| 原 M1 路线 | LLM 生成受限 Mapping，本地规则生产内容 | 人工端到端验证存在持续失败 | 退出通用生产主路径 |

### 3.1 Route B

模型接收原始文件、用户指令和授权业务数据，使用 Hosted Code Interpreter 完成文件处理，并返回实际 XLSX。

优势：

- 已有真实两轮文件生产证据。
- 无需自建 Python 执行沙箱。
- 可以将上一轮文件作为下一轮输入。
- 无需为每种内容修改预先扩展 Mapping 指令。
- 与现有 Responses Adapter 具备直接集成基础。

限制：

- 依赖外部模型和托管执行服务。
- 需要管理 API 费用、延迟、文件传输与数据边界。
- 尚未证明复杂 Office 文件的完整保真能力。
- 尚未通过 Odoo 产品端到端验收。

### 3.2 Route C

模型生成完整表格内容描述，本地通用序列化器将其转换为 XLSX。

本次两轮合计仅使用 889 tokens，成本具有吸引力。

但当前证据仅覆盖简单表格，不能证明对公式、样式、图表、命名区域等复杂工作簿特性的完整保留。因此，不作为当前通用编辑主路线。

### 3.3 Route D

模型生成 Python 脚本，由本地隔离 Worker 执行。

该路线技术上具有可行性，但尚未进行同等实测。与 Route B 相比，需要自行承担代码执行隔离、依赖管理、资源限制及运维工作。

鉴于 Route B 已通过目标用例验证，且成本可以接受，当前没有必要为选择 Route D 再启动完整路线论证。保留其作为未来特定部署或成本条件下的备选方案。

## 四、TV 验证证据

### 4.1 测试对象

文件：`contact1.xlsx`

原始文件包含：

- 一个工作表。
- A1～C1 三个表头。
- 无预先填充的数据行。

数据来源：当前 Odoo 用户可访问的三条真实 `res.partner` 记录。

### 4.2 第一轮

用户要求：根据 Odoo 联系人数据填写 Excel。

Route B 实际完成：

- 读取原始 XLSX。
- 填充三条联系人。
- 保留原有表头。
- 返回可读取的 XLSX。
- 独立回读确认内容与授权数据一致。

**结果：PASS。**

### 4.3 第二轮

用户要求：增加地址列。

Route B 使用第一轮实际生成的 XLSX 作为输入。

实际完成：

- 新增 D 列地址。
- 保留 A～C 列原有内容。
- 地址与第二次授权数据查询结果一致。
- 返回可读取的 XLSX。

**结果：PASS。**

### 4.4 资源消耗

| 指标 | 实测 |
|---|---:|
| Responses 请求 | 4 次 |
| 输入 Token | 15,349 |
| 输出 Token | 4,901 |
| 总 Token | 20,250 |
| Route B 两轮 Token | 19,361 |
| Route C 两轮 Token | 889 |
| Code Interpreter 调用 | 14 次 |
| Hosted 容器 | 2 个 |
| 容器清理 | 全部完成 |

两轮任务的费用按此前讨论估算为几美分量级；实际账单金额尚未核实，不能将估算写成实测成本。

### 4.5 验证边界

以下能力尚未通过本次 TV 证明：

- 任意多工作表保真。
- 复杂公式与跨表引用。
- 格式、样式及条件格式保留。
- 合并单元格、Excel Table、命名区域。
- 图表、透视表、外部链接、宏和嵌入对象。
- 大型工作簿的完整处理。
- Odoo UI → Candidate → Accept → Current → Finalize 全流程。

TV 证明了选定路线的基本技术可行性，不等于完成产品验收。

## 五、目标架构

### 5.1 逻辑流程

```text
用户自然语言指令
        ↓
统一 AI Agent office Tool
        ↓
Odoo 授权业务数据读取
        ↓
LLM + Hosted Code Interpreter
        ↓
生成 / 修改 Office 文件
        ↓
返回 Candidate 文件
        ↓
Odoo 本地验证与风险识别
        ↓
用户确认 / 接受
        ↓
Current / Last Valid
        ↓
Finalize / 附件交付
```

### 5.2 职责分配

| 职责 | 所属组件 |
|---|---|
| 理解用户需求 | LLM |
| 分析 Office 内容与结构 | LLM + Hosted 执行环境 |
| 决定内容布局与修改逻辑 | LLM |
| 生成、编辑 Office 文件 | Hosted Code Interpreter |
| 查询真实 Odoo 数据 | Odoo 授权 Retriever |
| 执行 Odoo ACL/Record Rules | Odoo |
| 校验候选文件 | Odoo 本地验证服务 |
| 判断是否需要用户确认 | Odoo 治理规则 |
| 用户业务决策 | 用户 |
| 管理文件版本 | Odoo |
| 记录审计证据 | Odoo |
| 最终文件交付 | Odoo |

### 5.3 架构硬约束

- **ARCH-01：统一工具入口。**对 AI Agent 只公开一个 `office` Tool。内部可以按职责分层，但不要求用户或 Agent 分别调用多个公开工具。
- **ARCH-02：内容生产通用性。**不依赖固定模板、工作表名称、单元格位置、Odoo 业务模型或字段。联系人、库存等仅作为测试用例，不得驱动特例化架构。
- **ARCH-03：LLM 主导内容生产。**不得将 M1 Mapping 或有限预定义操作集重新设为所有内容生产的强制前置条件。
- **ARCH-04：Odoo 权限不可绕过。**模型只能获得当前用户有权读取的数据。Hosted Code Interpreter 不持有 Odoo 数据库凭据、ORM 环境或服务器内部访问权限。
- **ARCH-05：用户最终业务决策权。**系统可以发现风险、提示并要求确认，但不能替用户决定是否接受可确认的业务风险。用户有效确认后，必须在确认范围和约束条件内执行；权限、安全及技术限制不得通过确认绕过。
- **ARCH-06：文件版本与确认一致性。**Candidate 必须绑定来源文件版本、文件哈希及实际修改结果。确认后执行必须复核确认对象及版本有效性，避免对已变化的文件错误执行旧确认。
- **ARCH-07：生成成功不等于交付成功。**必须区分文件已生成、Candidate 已注册、用户已接受、Current 已更新、Finalize 已完成、附件已交付。不得以模型成功返回文件代替完整业务成功状态。

## 六、现有资产保留与调整

### 6.1 保留

- 当前用户授权 Retriever。
- OpenAI Provider 配置。
- Responses Adapter。
- 文件 Candidate 验证机制。
- Current / Last Valid / Revision。
- 用户 Accept / Confirmation。
- Finalize。
- 私有附件与 Discuss 交付。
- 审计、错误分类与文件哈希管理。

### 6.2 调整

1. **首次文件注册：**现有 `register_initial_v1` 依赖 M1 验证凭证。需要设计可信的模型生成文件初始化路径，使首次生成的 Candidate 可以经过验证与用户接受后建立 V1。不得直接由模型修改 Current 指针。
2. **公开 Tool 调度：**现有 Responses Adapter 已具备 XLSX 输入输出能力，但公开 M2 编辑入口仍受外部 Provider Dispatch 门禁限制。需要在明确授权策略后完成可信调度连接。
3. **内容生产主路径：**将原先以 Mapping 为中心的生产机制调整为 LLM-Native 文件生产机制。既有 Mapping 能力可作为历史兼容能力保留，但不再作为通用 Office 生产的架构前提。

### 6.3 不建议改动

本次路线调整不应无理由重写已经通过独立验证的版本、确认、权限和附件交付服务。采用最小必要改造，避免将内容生产架构调整扩大为整个 Office Engine 的重新开发。

## 七、主要风险及控制措施

| 风险 | 控制要求 |
|---|---|
| 模型生成错误内容 | 文件回读、数据比对、用户审核 |
| 复杂 Excel 特性丢失 | 结构及特性差异验证；不支持时明确告知 |
| Odoo 数据越权 | 仅通过当前用户授权 Retriever 提供数据 |
| 模型代码执行风险 | 使用托管隔离环境，不在 Odoo Worker 内执行生成代码 |
| 文件版本错乱 | 哈希、父版本、Candidate、Accept 绑定 |
| 用户确认失效 | 确认前复核版本及实际修改范围 |
| 外部服务失败 | 保留 Last Valid，不得错误更新 Current |
| API 成本变化 | 记录 Token、容器费用、延迟和任务成本 |
| 敏感数据外发 | 明确 Provider 数据处理边界、授权与保留策略 |
| 文件生成成功但交付失败 | 分层状态与可恢复交付机制 |

验证器应当是治理组件，而不是新的内容生产引擎。对于复杂文件，不得仅因 XLSX 能够打开，就认定内容和结构完整。

## 八、TDD 修订范围

本次 TDD 修订应聚焦以下主题：

1. 内容生产架构：以 LLM-Native 文件生成和连续编辑替代 Mapping 必经路径。
2. 统一 Tool 契约：保留单一 `office` Tool，对内调度授权数据、模型处理和版本治理。
3. 首次版本生命周期：定义 Raw Upload → Candidate → Accept → V1/Current 的可信流程。
4. 后续版本生命周期：定义 Current → LLM Edit → Candidate → Accept → New Current。
5. 验证与确认：区分完成、需确认、需澄清、阻断、失败，并保留用户最终决策权。
6. 复杂文件保护：定义可检测的结构变化、保真验证边界和不可验证情形。
7. 外部执行安全：定义文件传输、数据最小化、容器隔离、超时、清理及审计。
8. 端到端验收：以真实 Odoo UI、真实文件和真实模型调用为最终验收依据。

本次 TDD 修订不应重新开放已收口的技术路线选择，除非后续验证出现足以推翻 Route B 核心假设的新证据。

## 九、实施与验收建议

### 9.1 实施顺序

| 批次 | 建议范围 |
|---|---|
| CC-01 | 首次文件注册与统一调度：完成可信的首次 Candidate 注册、用户接受及 Responses Adapter 接入。 |
| CC-02 | 两轮真实 Excel 端到端闭环：在 Odoo UI 中完成上传 `contact1.xlsx`、填写三条联系人、用户接受、增加地址列、再次接受、Finalize、下载并核对文件。 |
| CC-03 | 复杂 Excel 回归：覆盖多工作表、公式、样式、合并单元格、表格、命名区域等实际业务文件；不以“文件能打开”作为唯一成功标准。 |
| CC-04 | 异常、权限与交付验证：验证越权访问、模型失败、验证失败、确认失效、重复请求、并发版本冲突及附件交付异常。 |

以上为建议拆分，最终以冻结后的 TDD 和 Implementation Plan 为准。

### 9.2 验收原则

必须区分三类证据：

- **单元测试：**证明组件行为符合契约。
- **技术验证：**证明模型和文件处理能力真实可用。
- **人工端到端验收：**证明业务用户能够通过 Odoo 完成实际任务。

单元测试数量不能替代人工端到端验收。

### 决策重新打开条件

仅在出现以下实质证据时重新评审路线：

- Route B 在代表性真实文件上持续无法满足核心需求。
- 复杂文件保真问题无法通过合理验证和保护机制控制。
- 外部数据处理条件不符合业务或合规要求。
- 成本、延迟或服务限制显著超出正式批准的运行预算。
- Odoo 治理机制无法可靠接收或管理模型生成的文件。

一般性 Bug、单次模型失败或局部接口问题，应先按工程缺陷处理，不自动触发路线重选。

## 十一、最终决策

Route B 作为 Office Engine 下一版内容生产技术路线已选定。后续 TDD 架构修订仍须按项目变更流程单独评审和批准。

本次技术路线调整的核心不是放弃本地 Python，也不是取消本地验证，而是重新划分职责：

> 由 LLM 负责决定并生产 Office 内容，由 Odoo 负责确保业务权限、文件版本、用户决策和交付过程受控。

现有 TV 已经证明该路线能够完成简单 XLSX 的连续两轮真实修改；下一阶段的任务是将已验证的文件生产能力接入 Odoo 产品流程，并逐步证明复杂文件的可靠性。

**冻结状态：**Route B 技术选型已冻结；TDD 修订待单独批准；生产上线尚未批准。
