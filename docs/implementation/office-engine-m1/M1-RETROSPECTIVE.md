## 2. 必须讨论的问题

### 2.1 防卫过当与正常业务瘫痪

> “为什么我们在 M1 初期写出了‘一刀切拦截’的代码？后续如何避免过度防御导致正常业务瘫痪？”

建议讨论：

- 哪些冻结契约或不完整能力模型导致“Office 文件一律拒绝”成为默认路径？
- 安全拒绝是否区分了恶意/伪装文件、格式有效但能力未覆盖的文件、以及已支持的正常文件？
- 如何在设计评审中同时要求负向安全测试和至少一条合法文件的正向黄金链路？
- 能力白名单如何基于真实样本逐项扩展，并避免把未识别对象等同于整个文件不安全？
- 错误状态和恢复行为如何让用户知道是“不支持”“需要澄清”还是“服务失败”？

**期望输出：** 形成一套 Office/LLM 功能变更的双向验收门禁：合法输入可完成预期业务路径；恶意、不支持和资源超限输入被精确拒绝；两类结果都留有可审计证据。

### 2.2 带着技术债推进 UI 验证

> “如何评价我们‘带着 spawn 和 handoff 的技术债强行推进 UI 验证’的战略决策？”

建议讨论：

- 将安全拒绝 UI 与成功生成 UI 分开验证，是否帮助了快速确认聊天组件，又是否导致团队把“红色拦截提示”误当作产品闭环？
- 哪些独立 UI 适配可以在后端服务未就绪时推进，哪些 UI 验收必须等待真实服务 handoff 和成功结果交付？
- 风险豁免应如何限制范围、有效期和回收条件？哪些事项不得以特批替代功能证据？
- 后续 E2E 是否要把“正常文件成功路径”设为前置验收，再验拒绝路径、普通附件回归和跨轮次隔离？
- 如何确保单个样本补验能补充证据，但不静默改写冻结 CC/FR 的历史状态？

**期望输出：** 确立“风险可并行处理、依赖必须可见、验收不可跳步”的门禁规则；区分开发放行、阶段验收和产品发布批准。

### 2.3 M2 AI 映射需求中的确定性约束

> “为了防止 M2 阶段 AI 的幻觉污染业务，我们需要在 SRS 中增加哪些确定性的约束？”

建议评审并决定以下条款是否纳入 M2 SRS：

1. **受约束的映射输出：** AI 只能返回版本化、严格 Schema 校验的 Mapping Plan；未知字段、元素、操作、模型、类型和额外键一律拒绝，不允许模型输出 Python、路径、公式或任意执行指令。
2. **数据来源可追溯：** 每个写入值必须关联用户明确输入或经 Odoo 权限网关读取的模型/记录/字段；没有证据来源的内容不得自动填入。建议输出映射来源标识与置信/不确定状态，不能把置信分数当作权限或正确性的替代。
3. **权限由 Odoo 决定：** AI 不直接访问数据库、ORM 或任意模型；服务端以当前用户 ACL、Record Rules、公司范围和字段白名单读取实时值，并在执行前再次验证授权。
4. **不确定时澄清：** 字段歧义、多个候选值、类型不匹配、冲突约束、未授权字段、未知模板元素或日期/金额单位不明确时停止自动执行，向用户展示具体待确认项。
5. **模板和公式保护：** 可写目标必须来自服务端解析结果且位于允许操作集；公式、只读元素、未知结构和未声明目标不得被 AI 改写。输出后由独立回读器核验目标值、公式表达式和声明结构。
6. **事实不得由模型伪造：** 记录值、命中记录、计数、权限结论、附件状态和下载链接均以 Odoo/Office 后端结果为准；模型只可解释结构化结果，不得补造业务事实。
7. **确认和幂等：** 规定何种 Mapping Plan 必须经用户确认；确认应绑定模板哈希、记录版本/读取快照、映射计划版本和当前请求 ID；重复提交不得生成不一致或重复的结果。
8. **失败无交付：** 校验失败、权限变化、超时、解析器警告、输出回读失败或结果附件持久化失败时，结果不得下载；错误反馈需区分拒绝、澄清、无结果和系统失败。
9. **多轮上下文边界：** 明确追问可继承哪些已确认条件；新一轮不得沿用未确认推断；相互冲突的追问必须澄清。
10. **提示注入与附件不可信：** 模板文字、隐藏工作表、文档批注/元数据和附件内容均视为不可信输入；只能作为映射参考，不能覆盖系统规则、工具权限或白名单。

**期望输出：** 决定哪些属于不可协商的业务规则，哪些属于非功能要求，哪些需通过 TDD/CC 定义；所有要求应有可测试的 Given/When/Then 验收标准。

## 3. 归档证据讨论

- CC-001/002/003 的 `SATISFIED` 仅代表对应冻结契约范围。
- CC-004/005 的行政关闭不改变其 FR 的 `NOT SATISFIED` 结果；后续补充成功证据应通过复评追加，不覆盖原 ATR。
- CC-OFFICE-M1-PRE-ROUTE-FIX 的通过范围是伪装附件拦截和普通附件回归，不等于通用 handoff 已通过。
- CC-006 按负责人批准的 MVP 范围关闭；复杂 XLSX 样本有完整聊天生成/下载证据，复杂 DOCX 的浏览器上传/下载仍未验证。
- 原始 TV 总体 Partial、P0-A/P0-B Partial、生产容量及 Queue Job 容量 INCONCLUSIVE 保持原状态。

## 4. M2 SRS 评审准备清单

- 从现有 M1 SRS 的 M2 范围、AI Mapping 和用户确认需求提取候选需求，不预先写入未经业务确认的产品行为。
- 组织至少一个 Excel 和一个 Word 的真实模板样本，列出映射目标、错误/歧义示例和可验证预期输出。
- 明确业务模型记录选择方式、权限模型、公司隔离、字段白名单的责任人及审查机制。
- 明确 Mapping Plan 的 Schema 版本、字段来源证明、澄清交互和人工确认策略。
- 定义失败状态、附件交付、幂等、多轮对话、数据新鲜度和审计要求。
- 为每项 P0 需求写 Given/When/Then；至少包括正常生成、拒绝未授权字段、澄清歧义、公式保护、回读失败和重复提交。
- 以 M1 最终交付报告、原始 TV、CC FR/ATR/HVR 和用户验收记录为输入，保留 M1 的已知限制和技术债，不把它们当作已完成能力。
