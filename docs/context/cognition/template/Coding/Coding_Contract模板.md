## 0. 文档治理

### 0.1 目的
Coding Contract（CC）是单次开发任务 / Sprint / Intent / Fix / Refactor 的执行边界契约。
它冻结：本次允许改什么、必须做什么、禁止做什么、什么条件下算完成。

### 0.2 核心原则
- CC 不得重新发明 SRS。
- CC 不得重新发明 DDD。
- CC 不得重新发明 TDD。
- CC 只冻结"本次实现边界"。

### 0.3 上游基线
- SRS（必选）：冻结业务事实。
- DDD（按需，仅复杂项目）：冻结领域结构。
- TDD（必选）：冻结技术方案。
- CC（本文档）：冻结执行范围。

### 0.4 编号体系（CC 自有编号）
CC 仅定义 4 套前缀。其他所有引用直接使用上游 ID，不另设编号。
Scope、Guardrail、Stop Conditions、Done Gate 均不单独编号。

| 前缀 | 用途 | 示例 |
|------|------|------|
| CC-CHANGE | 变更项 / 文件级边界 | CC-CHANGE-001 |
| CC-PRESERVE | 既有行为保留 | CC-PRESERVE-001 |
| CC-TEST | 测试契约项（可选；也可直接引用 TEST-xxx） | CC-TEST-001 |
| CC-DEC | 本次实现决策 | CC-DEC-001 |

上游 ID 直接引用：
- SRS：FR-xxx、BR-xxx、CFG-xxx、NFR-xxx、AC-xxx
- DDD（如适用）：AGG-xxx、ENT-xxx、INV-xxx、DS-xxx、DV-xxx、DD-xxx
- TDD：T-xxx、ORM-xxx、SVC-xxx、ADPT-xxx、Q-xxx 等
- 测试：TEST-xxx

### 0.5 三级治理（继承自 TDD §0.4）
① 工程强制标准 → 固化于模板
② 模板变量 → `{变量}`，按任务填写
③ 本次实现决策 → 记录于 CC-DEC

### 0.6 冻结规则
凡进入正式编号体系（CC-CHANGE / CC-PRESERVE / CC-TEST / CC-DEC）的内容均属已治理的执行契约，不得被 AI 静默修改。

### 2.3 TDD 引用（必选）
| TDD ID | 标题 | 相关性 |
|--------|------|--------|
| ORM-xxx | ... | ... |
| T-xxx | ... | ... |

### 2.4 Bug Report / 事件报告（如适用）
Bug Report / Issue / 生产事件可作为**问题证据**（证明当前行为有误）。
它们不得作为新增业务语义或技术设计的权威来源。
决策链：
Bug Report → 证明当前行为有问题
SRS → 决定期望业务行为
TDD → 决定技术修正方式
CC → 授权本次修复范围

### 2.5 追溯规则
CC 中任何**新增业务行为、业务规则、领域语义或架构级技术决策**，若无法追溯到 SRS / DDD / TDD，则不得进入 Implementation。**实现级局部决策**可记录为 CC-DEC，但不得改变上游语义、突破 TDD 技术边界或扩大本次 Scope。
若编码过程中发现缺失或冲突，必须停止并升级（见 §12）。

## 3. 范围冻结

### 3.1 在范围内（In Scope）
- {具体包含的行为、功能或修复}

### 3.2 超出范围（Out of Scope）
- {明确排除；AI 不得触碰}

### 3.3 非目标（Non-Goals）
- {看起来相关但不是本次目标的事项}

### 3.4 仅限范围的追溯规则
本次 CC **声明纳入 Scope** 的每个上游 ID，必须至少对应一个 CC-CHANGE 落地项（防遗漏）。
**未纳入本次 Scope 的上游需求/设计，不因本 CC 而自动获得实施授权。**
本 CC 不要求覆盖完整 SRS/TDD 基线的全部编号。

## 4. 变更边界

### 4.1 允许
| 类型 | 详情 |
|------|------|
| 文件 | `{path/to/file.py}` |
| 模型 | `{model.name}` |
| 字段 | `{model.field}` |
| 方法 | `{model.method}` |
| 新增文件 | `{path/to/new_file.py}` |

粒度规则：边界必须精确到足以防止 AI 误改。
高风险变更（权限、公共接口、核心模型）应采用能够明确限制实际修改面的**最小合理粒度**——可为文件、模型、字段、方法、接口或 XML/JS 组件。**不机械要求方法级。**

| 其他模块 | 禁止修改 |
| 公共 Adapter 接口 | 禁止修改 |
| ... | ... |

## 7. 适用的 TDD 防护栏（裁剪，不复制）

本节引用 TDD §18 中适用的 `T-xxx`。**CC 不复制或改写 Guardrail 规范性正文。**

| TDD 防护栏 | 适用性 | 本次落实位置 | 验证方式 |
|-----------|--------|------------|---------|
| T-SEC-001 | 适用 | `{落实处}` | `{TEST-xxx}` |
| T-CONC-002 | 适用 | `{落实处}` | `{TEST-xxx}` |
| T-TRX-001 | 不适用 | — | — |

**SSOT 规则**：CC 仅引用冻结 TDD 版本及 T-xxx ID。Guardrail 正文归属 TDD。若 TDD v1.1 修改了 T-CONC-002，历史 CC 中引用的 T-CONC-002 指向 §2.3 声明的 TDD 版本。

CC 可在 CC-DEC 中增加本次特定实现约束，但必须能追溯到 TDD 技术决策或明确标记为实现级局部约束。CC 不得创造新的业务规则。

## 12. 停止条件 / 升级闸门

出现以下任一情况时，AI / 开发者**必须停止自行扩展实现**：

| ID | 触发条件 | 升级路径 |
|----|---------|---------|
| 1 | SRS 缺失业务规则 | → SRS 修订 |
| 2 | SRS AC 无法满足 | → SRS 修订 |
| 3 | DDD INV 与实际实现冲突 | → DDD 修订（如项目有 DDD） |
| 4 | TDD 技术设计不足 | → TDD 修订 |
| 5 | 需要新增核心模型 | → TDD 修订 |
| 6 | 需要改变业务状态 | → SRS 修订 |
| 7 | 需要改变数据权威关系 | → DDD/TDD 修订 |
| 8 | 需要改变外部 API 契约 | → TDD 修订 |
| 9 | 需要改变权限语义 | → TDD 修订 |
| 10 | 需要引入新核心依赖 | → TDD 修订 |
| 11 | 将突破 Out of Scope | → CC 修订 |
| 12 | 原 CC 本身有误 | → CC 修订 |

**绝对禁止**："为了让代码跑通，直接自行补一个设计。" 停止。升级。

## 13. 完成定义 / 关闭标准

本节定义完成标准。**不在 CC 起草阶段填写最终执行结果。**
实际证据由 IHR / ATR / HVR 提供。Final Report 判断证据是否满足本标准。
最终 Merge / Release 仍由人工 Review Gate 决定。

| ID | 标准 | 闸门类型 |
|----|------|---------|
| 1 | 所有 In-Scope 项均有对应 CC-CHANGE 实现 | 硬闸门 |
| 2 | 未违反任何禁止区域 | 硬闸门 |
| 3 | 所有适用的 T-xxx 已验证（通过 TEST-xxx） | 硬闸门 |
| 4 | 所有 CC-PRESERVE 行为确认未变 | 硬闸门 |
| 5 | 如本 CC 存在必须人工验证的行为，HVR 已完成且通过 | 硬闸门（如适用） |
