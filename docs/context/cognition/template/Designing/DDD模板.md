## 0 文档治理与 DDD 适用性

### 0.1 DDD 适用条件（Decision Gate）

> **DDD 不是所有项目的必经文档。** 本模板专用于**复杂领域建模**；简单项目不得使用本模板，以免把简单问题过度设计。

DDD 是**复杂项目中**位于 SRS 与 TDD 之间的**可选领域设计层**。

- 当 SRS 已足以直接支撑 TDD（简单 CRUD、报表、Wizard、单模型增强、低复杂度功能）时，**可跳过 DDD，直接进入 TDD**；
- 当存在以下任一情形时，**应建立 DDD**：
  - 复杂领域边界、多个核心业务对象；
  - 复杂生命周期（状态、阶段、版本）；
  - 数据权威冲突（谁拥有最终事实）；
  - 重要业务不变量（INV）；
  - 跨对象一致性、跨领域协作。

**标准流程：**

```
简单项目：  SRS ──────────────────────────▶ TDD
复杂项目：  SRS ──▶ DDD（本模板）──▶ TDD
```

**适用性判定输出物（Decision Gate）：**

| 判定项 | 结论 |
| --- | --- |
| 是否存在复杂聚合边界 | {是 / 否} |
| 是否存在多个核心业务对象 | {是 / 否} |
| 是否存在复杂生命周期 | {是 / 否} |
| 是否存在数据权威冲突 | {是 / 否} |
| 是否存在重要业务不变量 | {是 / 否} |
| 是否存在跨领域一致性问题 | {是 / 否} |
| **结论** | **{采用 DDD / 直接进入 TDD}** |

> 判定结论须记录在本文档第 13 章 Domain Decision（DD-），作为是否建立 DDD 的依据。

### 0.2 本文档回答什么 / 不回答什么

DDD 定义**业务概念如何组织、谁是权威、什么是一致性边界**。它**不重新定义业务需求**——SRS 是业务契约的唯一权威来源。

**回答（领域结构 WHAT / HOW the domain is structured）：**

- 聚合边界、聚合根、实体、值对象；
- 领域对象的职责；
- 数据权威关系与派生投影方向；
- 生命周期的**领域归属**（属于哪个聚合、由哪个领域行为改变）；
- 业务不变量（INV）与一致性约束；
- 领域服务、领域事件的划分；
- 并发、幂等、跨聚合一致性的**业务语义**；
- 审计与追溯的**业务语义**；
- 领域策略、配置的领域建模方式。

**不回答（HOW of implementation → 属 TDD）：**

- 具体 ORM 字段类型、`_columns`、`_sql_constraints`；
- 数据库索引、锁的 SQL 写法（`SELECT ... FOR UPDATE`）、乐观/悲观锁实现——**归 TDD**；
- 并发控制实现：乐观锁 / 悲观锁 / 版本号 / 排他锁 / 事务隔离级别（**归 TDD 第 10 章**）；
- 重试、幂等、队列、消息中间件（**归 TDD**）；
- 异步队列、cron、worker、重试计数；
- HTTP/RPC、Adapter 接口、第三方协议；
- UI、前端组件、按钮交互；
- 具体审计字段（`create_uid`、`write_uid`、chatter）——**归 TDD**；
- 数据迁移脚本、环境策略、执行步骤——**归 TDD / Deployment Plan**；

> 若 TDD 阶段发现本 DDD 存在矛盾或遗漏，**单纯技术方案调整不得修改已冻结 DDD**；若属于领域契约本身的矛盾、遗漏或不可满足约束，**必须发起领域勘误**，不得由技术设计自行改变领域语义。

### 0.3 与其他文档的边界

| 文档 | 层 | 职责 | 不得越界 |
| --- | --- | --- | --- |
| SRS | 业务契约 | 做什么、业务规则、验收、**业务状态机** | 不定义对象结构 |
| **DDD（本模板）** | 领域模型 | 概念组织、权威源、一致性、**状态归属** | 不定义 UI/HTTP/队列/cron/ORM/锁实现 |
| TDD | 技术设计 | 模型/服务/Adapter/Schema/锁/事务实现 | 不重新定义业务语义或状态语义 |

> SRS 是业务状态、状态含义、允许/禁止流转的唯一权威；DDD 只定义这些状态在领域模型中的**归属**。

### 0.4 编号规则

统一采用 `{类型}-{域}-{序号}`（与 SRS 一致）。核心类型：

- 聚合：`AGG-{域}-01`
- 实体：`ENT-{域}-01`
- 值对象：`VO-{域}-01`
- 业务状态：`STATE-{域}-01`
- 不变量：`INV-{域}-01`
- 幂等键：`IDEMP-{域}-01`
- 领域服务：`DS-{域}-01`
- 领域事件：`EVT-{域}-01`
- 领域决策：`DD-{域}-01`
- Domain Verification：`DV-{域}-01`
- 验收标准：**使用 `DV-{域}-01`（不使用 `AC-`，AC 是 SRS 的业务验收标准）**

> 编号一旦分配永久不回收；新增追加序号，废弃仅标记「废弃」，不重用。

### 0.5 规范措辞

- **必须 / 禁止 / 不得**：领域强制不变量，不满足即视为模型错误。
- **应 / 不应**：原则性要求，例外须经评审。
- **可 / 允许**：被允许的行为，一旦进入 INV/STATE 即为正式契约。
- **建议 / 推荐**：非规范性说明，不作为验证依据。
- **支持**：不能单独表示约束强度，应与"必须 / 应 / 可"组合使用。

> 凡进入正式编号体系（AGG / ENT / VO / INV / STATE / DS / EVT / IDEMP / DV / DD）的内容均为正式契约。

### 0.6 单一事实来源（SSOT）

同一业务事实只允许在一个章节正式定义，其他章节通过编号引用，不复制正文。领域事实与唯一定义位置：

- Bounded Context 边界 → 第 1 章
- SRS → Domain 映射 → 第 2 章
- 聚合边界 → 第 3 章
- 实体字段 → 第 4 章
- 数据权威关系 → 第 5 章
- 状态归属 → 第 6 章（状态**语义**归 SRS）
- 不变量 → 第 7 章
- Domain Verification → 第 14 章
- 追溯 → 第 15 章

> 跨章节引用一律使用编号，禁止复制规则正文（避免双源维护漂移）。

## 3 聚合与一致性边界

> 聚合用于定义**必须保持一致的业务边界**。聚合根负责保护聚合内部不变量；外部不得绕过聚合根直接改变聚合内部业务状态。

### 3.1 聚合清单

| 聚合 | 聚合根 | 内聚实体 | 值对象 | 不变量 |
| --- | --- | --- | --- | --- |
| AGG-{域}-01 | {根} | {子实体…} | {VO…} | INV-{域}-01… |
| AGG-{域}-02 | {根} | — | {VO…} | INV-{域}-03… |

### 3.2 聚合根职责

> 通用聚合根职责模板（具体项目按需裁剪）：

- 聚合根必须是**创建 / 修改 / 状态变化**的统一入口；
- 聚合内子实体**不得脱离根独立存在**，不得被 UI / 外部服务直接 CRUD；
- 聚合内部必须保护自身不变量（INV）；
- 跨聚合通信**不得直接修改其他聚合内部状态**。

### 3.3 聚合数量原则

> 一个 Bounded Context 可包含一个或多个聚合。聚合数量**完全由业务一致性边界决定**，不与 Odoo module、数据库表、页面、菜单形成固定对应关系。

> **不得为了套用 DDD 模式而人为创建聚合。** 若多个对象不存在必须共同一致的业务不变量，不应强行合并为一个聚合。

## 5 数据权威与所有权

> **核心章节**：明确「权威源」与「派生投影」，禁止反向覆盖。复杂项目最常见的争议点即"谁拥有最终事实"。

### 5.1 权威源定义

> 每个业务概念指定唯一权威来源（Single Source of Truth）。

| 概念 | 权威源 | 性质 |
| --- | --- | --- |
| {业务结果} | `ENT-{域}-01` | 人工/业务确认后的权威数据 |
| {历史候选} | `VO-{域}-0X`（候选快照） | 外部产生的候选，**非权威** |

原则：

- 权威源唯一，所有对该概念的可变写入只经过权威源；
- 候选、外部原始值、快照**不得**被当作权威业务事实。

### 5.2 派生投影

> 为兼容或性能产生的投影对象，必须由权威源**单向生成**。

- 投影方向：**权威源 → 投影**（单向）；
- **投影不得反向成为该业务事实的权威来源**；
- 投影与权威源不一致时，**必须能够依据权威源恢复正确领域状态**；
- 投影的同步 / 异步、事务、重建策略**由 TDD 决定**，DDD 只规定投影方向与单向性。

> DDD **不规定**具体重建机制；同步重建、异步重建、定时重建等决策**归 TDD**。

### 5.3 候选 / 外部数据采纳规则（按需）

> 仅在项目存在候选、外部原始数据、重跑/刷新等概念时使用本章。DDD 只提出问题，**不固定答案**。

需明确：

1. 哪类数据属于**候选**而非权威；
2. 谁有权把候选**提升**为权威；
3. 候选**能否覆盖**既有权威；
4. 冲突时**以谁为准**；
5. 是否**必须保留候选历史**。

> 采纳规则的具体内容（如"人工确认后才采纳""重跑不覆盖已确认字段"）由具体项目在 SRS 中定义，DDD 负责将其转化为权威/候选的所有权边界。

## 6 生命周期与状态归属

> **SRS 是业务状态、状态含义、允许/禁止流转的唯一权威来源。** 本章**不得重新定义或修改 SRS 状态机**，仅定义这些状态在领域模型中的**归属**及其领域行为承载。

DDD 负责回答：

- 该状态**属于哪个聚合**；
- **哪个聚合根**拥有状态变化权；
- **哪个领域行为**触发状态变化；
- 状态变化受**哪些 INV** 保护；
- 状态变化产生**哪些领域事实**。

| SRS 状态 | 所属聚合 | 状态变化领域行为 | 关联不变量 | SRS 来源 |
| --- | --- | --- | --- | --- |
| `{待处理}` | AGG-{域}-01 | `submit()` | INV-{域}-04 | FR-XXX-01 / BR-XXX-02 |
| `{处理中}` | AGG-{域}-01 | `confirm()` | INV-{域}-05 | BR-XXX-03 |
| `{已完成}` | AGG-{域}-01 | `complete()` | INV-{域}-06 | FR-XXX-04 |

> 技术运行态（队列排队 / 执行中 / queued / running 等）**不属本章**，归 TDD。

## 7 Domain Invariants（INV-）

> 不变量 = 在**有效领域状态下始终必须成立的业务条件**（比"业务规则"更强）。

**严格定义：** INV 必须是业务条件，不得以技术/架构规则冒充。例如：

- ✅ "同一 Customer Quote 最多只能存在一个有效 Supplier Order"
- ✅ "已记录实际作业的作业单不得直接取消"
- ✅ "Pallet 仍存在库存时，其生命周期不得结束"
- ❌ "排他锁必须在短事务内释放"（属 TDD）
- ❌ "一个聚合根一个事务"（属架构原则，非领域不变量）

| 编号 | 领域约束 | 所属聚合 | SRS 来源 |
| --- | --- | --- | --- |
| INV-{域}-01 | {业务不变量} | AGG-{域}-01 | BR-XXX-03 |
| INV-{域}-02 | {业务不变量} | AGG-{域}-02 | FR-XXX-05 |

**来源规则（防止 DDD 自行发明业务）：**

- 每条**业务 INV** 必须追溯至 SRS 的 FR / BR；
- 无法追溯的 INV 必须明确标识为 **「领域结构约束」**（如聚合边界本身），并在第 13 章 DD- 记录理由；
- **禁止借 DDD 新增业务要求。**

## 8 Domain Services

> 承载**具有明确领域语义、但不自然属于单个 Entity 或 Value Object** 的业务行为。

### 8.1 Domain Service 定义

| 服务 | 职责 | 不持有 |
| --- | --- | --- |
| DS-{域}-01 | {跨实体业务行为，具明确领域语义} | 不持有基础设施 |

- 领域服务**只编排领域对象**，不暴露为 RPC，不处理传输细节；
- 其输入/输出均为领域对象或值对象。

### 8.2 Domain Service ≠ Application Service（重要）

**以下不属于 Domain Service：**

- ORM 加载 / 保存（Repository / Application 层）；
- 事务编排（Transaction management）；
- API / HTTP 调用；
- 消息分发、通知发送；
- UI workflow、流程编排；
- Repository 编排、基础设施重试。

> 跨聚合 workflow（如"加载 A → 调用外部 → 保存 B → 发通知"）属于 **Application Service**，归 TDD，不得伪装为 Domain Service。

## 9 Domain Events（EVT-，按需）

> 表达领域事实"已发生"，用于跨聚合协作的解耦。**Domain Event ≠ 异步消息。**

| 事件 | 触发时机（领域事实） | 携带业务信息 | 消费者 |
| --- | --- | --- | --- |
| EVT-{域}-01 | {状态流转至 X} | {业务上下文} | {下游聚合} |

原则：

- 聚合不得直接修改其他聚合内部状态；
- 跨聚合协作可通过**领域事件、领域服务或应用层协调**表达；
- 事件的处理方式（**同步 / 异步、是否消息队列**）**属 TDD 实现选择**，DDD 只定义领域事实与协作关系。

## 10 跨聚合协作、并发与幂等的领域语义

> **仅定义业务并发场景下必须成立的合法结果**，不含任何技术实现机制。

### 10.1 并发与幂等的业务语义（INV-CONC-）

| 编号 | 业务并发场景 | 必须保证的业务结果 | SRS 来源 |
| --- | --- | --- | --- |
| INV-CONC-01 | 多人同时确认同一对象 | 最多只有一个有效确认成功 | BR-XXX-01 |
| INV-CONC-02 | 同一请求被重复提交 | 不得产生重复有效业务结果（幂等） | BR-XXX-02 |
| INV-CONC-03 | 确认与取消同时发生 | 最终只能存在一个合法业务状态 | BR-XXX-03 |

> 上述 INV 描述"业务上什么结果合法"，即领域契约。

### 10.2 跨聚合一致性

- 聚合用于定义必须维护一致性的业务边界；
- **聚合内部必须保护自身不变量**；
- **跨聚合一致性方式依据业务要求决定**，可采用同步协调或最终一致，**不得仅因技术便利扩大聚合边界**；
- 聚合不得直接修改其他聚合内部状态。

### 10.3 实现机制归属（TDD）

> 以下**全部由 TDD 定义**，不得出现在 DDD 中（均属实现机制）：

乐观锁、悲观锁、数据库唯一约束、事务隔离级别、版本号、`SELECT ... FOR UPDATE`、SQL Lock、Retry、Queue、消息中间件、savepoint——**以上归 TDD 第 10 章**。

## 11 领域策略与配置建模（按需）

> SRS 的 CFG（配置需求）在领域模型中如何承载。本章**不假设所有项目都存在 Mapping**。

SRS CFG 可根据语义落成以下任一领域元素：

- Value Object（VO）
- Policy / Rule Set
- Entity
- Domain Service 的输入参数

| 编号 | 配置项 | 业务含义 | 作用范围 | 可维护角色 | 变更生效范围 |
| --- | --- | --- | --- | --- | --- |
| CFG-{域}-01（SRS） | {配置项} | {业务含义} | {作用范围} | {配置管理员} | {仅影响新任务 / 影响所有未完成任务} |

原则：

- 领域策略/配置只输出**推荐候选**，匹配不到、多匹配、匹配错误均属正常；
- **策略引擎不得自动改写配置表**；
- 人工可覆盖候选，覆盖结果成为权威（见第 5.3 节）；
- 仅当项目**确实存在 Mapping 概念**时，才在项目中增设 `MAP-{域}-01` 等编号；**MAP 不是 DDD 标准固定类型**。

## 12 审计与追溯语义（按需）

> DDD 只定义**哪些业务动作必须可追溯、需保留哪些业务事实**；不固定具体存储字段。

| 业务动作 | 必须追溯的信息 | SRS 来源 |
| --- | --- | --- |
| `{Quote Accepted}` | 谁接受、何时接受、接受时 Quote 版本、关键金额 | BR-XXX-01 |
| `{业务动作示例：如单据核销}` | 操作人、时间、操作对象、业务结果 | FR-XXX-03 |

- 关键业务动作的**操作主体、时间、关键前后值**须可追溯；
- 原始数据、地址、引用字段遵循授权访问；
- **具体 Odoo 字段**（`create_uid` / `write_uid` / `write_date` / mail.thread / audit log / event table）**由 TDD 决定**。

## 13 Domain Decision（DD-）

> DDD 专属决策记录。技术选型归 TDD / ADR，不在本节。

| 编号 | 决策 | 原因 | 状态 |
| --- | --- | --- | --- |
| DD-{域}-01 | {选 A 聚合边界而非 B} | {业务一致性边界} | 已采纳 |
| DD-{域}-02 | {是否建立 DDD / 跳过 DDD} | {适用性判定} | 已采纳 |

> 若本次设计改变既有领域概念，DDD **只记录新旧领域语义之间的映射关系**；数据迁移脚本、环境策略、执行步骤**由 TDD / Deployment Plan 定义**（不在本模板范围内）。

## 14 Domain Verification（DV-）

> DDD 不使用 `AC`（AC 是 SRS 的业务验收标准）。DDD 使用 **DV = Domain Verification**，验证对象是**领域模型本身**。

DV 验证：

- INV 是否成立；
- 聚合边界是否保护了应有的业务一致性；
- 权威关系是否满足（投影未反向覆盖权威）；
- 状态归属是否正确（归属与 SRS 状态机一致）；
- 跨聚合行为是否保持了领域合法性。

**强制规则：**

> **每个关键 INV 至少有一个 DV；** 其他领域元素（AGG / ENT / VO）**仅在确有验证价值时**建立 DV，禁止为填满追溯矩阵而制造形式主义测试。

| DV | 验证对象 | Given | When | Then | 关联 |
| --- | --- | --- | --- | --- | --- |
| DV-{域}-01 | INV-{域}-01 | {领域前置状态} | {领域行为} | {必须成立的业务结果} | INV-{域}-01 |
| DV-{域}-02 | AGG-{域}-01 | {子实体存在} | 绕过 Root 直接改子实体 | 被领域模型拒绝 | INV-{域}-02 |

## 15 Traceability

> DDD 追溯矩阵**不是**复制 SRS 的 Requirement → AC，而是回答三个独立问题。

### 15.1 SRS → Domain（防需求丢失）

| SRS Requirement | Domain Element | 状态 |
| --- | --- | --- |
| FR-XXX-01 | AGG-{域}-01 | ✓ |
| BR-XXX-04 | INV-{域}-02 | ✓ |
| CFG-XXX-01 | VO-{域}-04 | ✓ |

> 每行证明：SRS 需求已被领域模型承载，无遗漏。

### 15.2 Domain → SRS（防 DDD 偷造业务）

| Domain Element | SRS 来源 | 说明 |
| --- | --- | --- |
| INV-{域}-01 | BR-XXX-03 | — |
| DS-{域}-01 | FR-XXX-08 | — |
| AGG-{域}-02 | — | **领域结构约束**（须有 DD- 说明） |

> 每行证明：DDD 元素均有业务来源。**无 SRS 来源的必须显式说明**（标记为"领域结构约束"并关联 DD-），不得默默新增业务。

### 15.3 INV → DV（关键约束可验证）

| INV | DV | 状态 |
| --- | --- | --- |
| INV-{域}-01 | DV-{域}-01 | ✓ |
| INV-{域}-02 | DV-{域}-02 | ✓ |

> 每个关键 INV 至少对应一个 DV（呼应第 14 章强制规则）。

## 附录 A Glossary（术语表）

| 术语 | 定义 |
| --- | --- |
| Bounded Context | 明确的领域边界，包含一组内聚的领域模型 |
