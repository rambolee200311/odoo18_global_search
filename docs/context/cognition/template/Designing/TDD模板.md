## 0 文档说明

### 0.1 文档定位

本文档是 **SRS 与 DDD（如建立）冻结之后的技术实现契约**，回答"**具体怎么实现**"。覆盖：技术栈、模块结构、ORM 模型、数据约束、报文 Schema、领域行为实现、外部 Adapter、异步队列、状态机技术态、并发与锁、异常、权限、UI、测试、可观测性、部署迁移与 Coding Contract 门禁。

文档链：

```
业务规范 / BRD → SRS（业务契约）
                    ↓
        DDD Decision Gate ── 简单项目：直接进入 TDD
                    ↓ 复杂项目
                DDD（领域结构） → TDD（本文档） → Coding Contract → Implementation / Test
```

DDD 为复杂项目按需文档；TDD 必须能**独立承接 SRS**（无 DDD 时自行推导实现结构），也能**完整承接 DDD**（有 DDD 时严格落地领域模型）。

### 0.2 上游基线

| 项 | 内容 |
|---|---|
| 上游业务基线 | SRS `{版本}`（**强制**，业务契约唯一权威） |
| 上游领域基线 | DDD `{版本}`（**按需**，领域结构权威；简单项目可不存在） |
| 下游 | Coding Contract、Implementation、Test |

> TDD 同时受 SRS 与 DDD 约束。若两者冲突，须先走 SRS/DDD 勘误；**技术实现不得自行改变业务或领域语义**。

### 0.3 本文档回答什么 / 不回答什么

| 回答（属于 TDD） | 不回答（属于 SRS / DDD） |
|---|---|
| 用什么 ORM 模型、字段、索引 | 业务实体是什么、业务状态含义 |
| 锁、事务、隔离级别、重试策略 | 并发时业务上必须保证什么结果（INV-CONC，属 DDD） |
| Adapter、超时、降级、熔断 | 外部系统业务目的与预期结果 |
| 异步队列、Worker、Cron 机制 | 哪些业务必须异步（业务契约，属 SRS） |
| `ir.model.access.csv`、Record Rule | 业务角色与业务权限（属 SRS） |
| 状态字段的技术映射、技术执行态 | 业务状态语义、允许/禁止流转（属 SRS） |
| Implementation Guardrails `T-xxx` | 业务规则 BR、领域不变量 INV |

### 0.4 内容治理：三类划分（评审总原则）

TDD 母模板允许包含组织级技术约束，但须区分"强制问题"与"强制答案"：

| 类型 | 母模板处理 | 示例 |
|---|---|---|
| **① 工程强制标准** | 固定写入模板，所有项目必须遵守 | 外部调用必须设超时、SQL 必须参数化、权限必须映射 SRS |
| **② 模板变量** | 必须填写，具体值由项目决定 | `{Odoo版本}`、`{Python版本}`、`{PostgreSQL版本}`、超时秒数、worker 数 |
| **③ 项目设计决策** | 提供设计位，不预先给唯一答案 | 是否异步、是否 Outbox、锁策略、状态存储结构、是否用 Adapter |

> **核心原则：母模板强制"必须回答的问题"和"组织已确定的工程规范"；变量由项目填写；未确定的技术方案由项目 TDD 作出并记录决策。**

凡出现"**评估 / 必须明确 / 按需**"字样，均属 ③，项目可自行决策但**不得留空不答**。

### 0.5 冻结与变更规则

- TDD 在 **SRS（及 DDD）冻结后**进入编码；冻结后**只做勘误、不覆盖、不删除**既有内容；
- 需求/领域变更 → 先改 SRS/DDD → 再同步本文件 → 版本升级；
- 技术方案调整（不改业务/领域语义）→ 可直接调整本文档并升级版本，**但不得反向要求修改 SRS/DDD**；
- 编号一经发布永久保留，新增追加，不回收。

### 0.6 编号规则

### 0.7 规范措辞

- **必须 / 禁止 / 不得**：组织级工程强制标准，违反即不合规；
- **应 / 不应**：原则性要求，偏离须书面理由；
- **必须评估 / 必须明确 / 按需**：项目设计决策，须给出本项目答案（属 ③，允许不同答案）；
- **可 / 允许**：实现上被允许的方式，一旦写入契约即为正式要求；
- **建议 / 推荐**：非规范性，不作为门禁依据。

## 3 ORM 模型设计

> 本章定义业务/领域对象到 Odoo ORM 的技术映射。
>
> - **存在 DDD 时**：承接 DDD Aggregate / Entity 边界，不得由 TDD 擅自改变领域归属；
> - **不存在 DDD 时**：直接根据 SRS 的业务对象、业务规则、状态及数据关系设计 ORM 模型；
> - ORM 模型、表及关系的具体拆分属于 TDD 技术设计，**不要求 Aggregate 与 ORM 模型形成固定 1:1 映射**。

### 3.1 模型映射

| 上游对象 | 来源 | ORM 模型 | 表名 | 职责 |
|---|---|---|---|---|
| `AGG-XXX-01` | DDD | `x.xxx` | `x_xxx` | 聚合根实现（如存在 DDD） |
| `ENT-XXX-01` | DDD | `x.xxx.line` | `x_xxx_line` | 内聚明细（如存在 DDD） |
| `{业务对象}` | SRS（FR/BR 对应） | `x.xxx` | `x_xxx` | 业务数据实现（无 DDD 时直接映射） |

> 简单项目（无 DDD）仅有"来源 = SRS"的行；不得为填写模板而虚构 `AGG-` / `ENT-` 编号。

### 3.2 字段契约

| 字段 | 类型 | 来源 / 权威关系 | 约束 | 上游引用 |
|---|---|---|---|---|
| `state` | Selection | SRS 业务状态映射（见第 9 章） | 见 `ORM-DATA-001` | SRS §7 |
| `{field}` | `{type}` | `{业务标准 / 权威源 / 派生投影}` | `{...}` | `{SRS FR/BR 或 DDD ENT}` |

> 字段来源分三类：**业务标准字段**（直接业务属性）、**权威源字段**（来自另一对象/外部权威）、**派生投影字段**（由权威源计算得出，不得反向覆盖权威，见 `T-DATA-001`）。无 DDD 时，"上游引用"列直接指向 SRS FR/BR。

| 方法 | 上游行为 | 事务边界 | 说明 |

## 7 外部服务 Adapter

> 外部网络调用**必须设置明确超时**（工程强制标准）。其余策略（是否重试、是否幂等、降级方式）**按接口逐项明确**（属 ③）。

### 7.1 Adapter 契约表

| Adapter | 外部对象 | Timeout | Retry | Idempotency | Failure 处理 | Degradation |
|---|---|---|---|---|---|---|
| `ADPT-AI-001` | `{AI 服务}` | `{秒}` | `{允许/禁止；哪些错误}` | `{如何实现}` | `{...}` | `{降级行为}` |
| `ADPT-CUR-001` | `{汇率服务}` | `{秒}` | `{...}` | `{...}` | `{...}` | `{...}` |

- **Timeout**：每个 Adapter **必须**填写明确秒数（属 ①）；
- **Retry / Idempotency / Failure / Degradation**：逐接口明确策略与业务影响（属 ③），不得笼统写"全部可重试"；
- 幂等键的业务语义（重复调用不得产生重复有效结果）属 DDD `INV-CONC`；具体 key 构成（如 `partner + external_reference`）属 TDD。

### 7.2 Adapter 接口定义

```python
class ExternalServiceAdapter(ABC):
    @abstractmethod
    def call(self, payload: dict) -> dict:
        """必须带超时；返回标准化结果或抛出领域异常（第 11 章）。"""
        ...
```

## 8 异步队列、Worker、Cron

### 8.1 执行方式评估（工程强制：必须评估）

> 若项目存在**长耗时任务或外部 IO**，TDD **必须评估**同步/异步执行方式，并依据 SRS NFR、用户等待时间、失败恢复要求及事务边界明确选择；采用异步时按本章完成设计。

**不强制所有项目使用 Queue**——"是否异步"属项目设计决策（③）。

| 场景 | 评估结论 | 理由 | 实现 |
|---|---|---|---|
| `{长耗时处理}` | `{同步 / 异步}` | `{依据 NFR-XXX}` | `{queue_job / 自研}` |

### 8.2 队列 / Worker

| 编号 | 任务 | 触发 | 并发 | 重试 | 死信 | 对应 DDD |
|---|---|---|---|---|---|---|
| `Q-JOB-001` | `{...}` | `{事件 / API}` | `{1 / 多}` | `{策略}` | `{处理}` | DS-INV-01 |

- 重试次数、退避策略、超时判定、死信队列在此定义；
- 任务与聚合根的事务边界：见 `T-TRX-001`（聚合内需原子维护的不变量同事务）。

### 8.3 Cron（不再限制为补偿/巡检）

> Cron **可用于**业务定时触发、周期同步、补偿、巡检等场景。所有 Cron **必须明确**：业务/技术职责、执行频率、幂等性、失败处理及重复执行影响。

| 编号 | 职责类型 | 频率 | 幂等 | 失败处理 | 重复执行影响 |
|---|---|---|---|---|---|
| `Q-CRON-001` | `{业务定时 / 补偿 / 巡检}` | `{...}` | `{...}` | `{...}` | `{...}` |

> 例：定时汇率更新属**业务定时触发**，是合法的核心业务流程，不应被模板禁止。

### 8.4 可靠投递（条件规则）

> 当**业务数据库提交与异步消息投递之间存在"业务已成功但任务/消息丢失"不可接受的一致性风险**时，TDD **必须**设计可靠投递机制；可采用**事务消息、Outbox 或经评审的等价方案**。

**不强制 Outbox**——只要解决"可靠投递"问题即可（③，允许等价方案）。若评估不存在该风险，明确说明"No Outbox 理由"即可。

## 9 状态机技术态

### 9.1 业务态与技术态映射

> 业务状态语义来自 SRS；TDD 负责定义其**技术字段映射**。若存在 `queued / running / retry / failed` 等技术执行态，**必须明确其承载对象及与业务状态的关系**，不得因技术运行态改变 SRS 已冻结的业务状态语义。

**不强制**业务态与技术态使用同一个 `state` 字段（属 ③）。项目可从以下方案自选其一：

| 方案 | 业务态承载 | 技术态承载 | 适用 |
|---|---|---|---|
| A 同字段 | `state` 同时枚举业务态与技术态（须保证语义无冲突） | 同 `state` | 简单、执行态少的场景 |
| B 独立字段 | 主对象 `state` = 业务态 | 主对象 `execution_state` = 技术态 | 执行态较多 |
| C 独立对象 | 主对象 `state` = 业务态 | 独立 Job 模型 `job.state` = 技术态 | 异步/重试复杂 |

### 9.2 映射表

| SRS 业务状态 | 技术字段映射 | 技术执行态（如有） | 承载对象 | SRS 来源 |
|---|---|---|---|---|
| `awaiting_review` | `state = 'awaiting_review'` | — | 主对象 | FR-INV-12 |
| — | `execution_state = 'running'` | `queued/running/retry/failed` | `{方案 B/C}` | INV-CONC-01 |

## 10 并发、事务与锁

### 10.1 并发控制策略（工程强制：必须评估）

> 每个存在**并发写入风险、唯一业务结果约束或 DDD `INV-CONC`** 的对象，**必须明确并发控制策略**（属 ③——策略本身可选，但**不得留空不答**）。

允许策略（包括但不限于）：

| 策略 | 适用 | TDD 实现要点 |
|---|---|---|
| 无需额外控制 | 无并发写入 | — |
| ORM / DB 唯一约束 | 天然唯一键 | 见 `ORM-DATA-001` |
| 原子写入 | 单条 UPDATE 可完成 | 使用 `UPDATE ... WHERE` |
| 乐观并发控制 | 冲突少、长事务 | 版本字段 `write_date` / 自定义 `version` |
| 悲观锁 | 冲突频繁、短临界区 | `SELECT ... FOR UPDATE`（见 `T-LOCK-001`） |
| 业务幂等 | 重复请求需安全 | 幂等键（见 7.1） |

> **重点：有并发风险必须有明确答案**——不强制"必须有锁"。

### 10.2 Guardrails

| 编号 | 规则 | 强度 |
|---|---|---|
| `T-LOCK-001` | 排他锁（如 `SELECT FOR UPDATE`）**不得跨越外部 IO**；临界区内禁止调用 Adapter、发送消息 | 工程强制（①） |
| `T-LOCK-002` | 持锁期间不得执行长耗时操作；异步任务须在锁释放后提交 | 工程强制（①） |
| `T-LOCK-003` | 锁等待超时必须显式配置，避免无限等待 | 工程强制（①） |
| `T-TRX-001` | 聚合内部需要原子维护的不变量及其内聚数据修改，必须在同一事务一致性边界内完成（**不**等同于"每次聚合操作只能一个 DB 事务"，亦**不**意味着"两个聚合绝对不能同事务"） | 工程强制（①） |
| `T-TRX-002` | 事务边界不得包含外部 IO（HTTP/RPC/文件） | 工程强制（①） |

> `T-LOCK-001/002`、`T-TRX-002` 等**锁实现、事务实现**是 TDD 职责（承接 DDD INV-CONC 的业务语义）；具体 SQL、ORM 写法属 Implementation。
>
> **SSOT**：`T-TRX-001` 为本文件事务规则唯一定义，§3.3、§6.2、§8.2 均**引用本编号**，不另行改写不同版本。本章 18.1 亦仅引用，不重复定义。

### 10.3 幂等实现

| 编号 | 业务幂等语义（来自 DDD） | TDD 幂等键实现 |
|---|---|---|
| `INV-CONC-02`（DDD） | 同一请求重复提交不得产生重复有效业务结果 | `idempotency_key = {partner} + {external_reference}` | `T-CONC-002` |

## 18 Implementation Guardrails / Coding Contract Baseline（`T-xxx`）

> 本章**不是**单次 Sprint/Intent 的 Coding Contract，而是 **Coding Contract 的上游技术门禁来源**：定义本模块实现**必须遵守**的工程约束基线。
>
> 单次 Coding Contract = 本次实现哪些 `T-xxx`、允许改哪些文件、禁止改哪些领域、测试哪些 TC、变更边界——由 Implementation 阶段依据本章基线裁剪生成。

### 18.1 门禁规则分组

| 编号 | 规则 | 强度 | 来源 |
|---|---|---|---|
| `T-SEC-001` | 密钥不得写日志 | 强制（①） | SRS NFR |
| `T-SEC-003` | SQL 必须参数化 | 强制（①） | 组织级标准 |
| `T-DATA-001` | 派生投影不得反向覆盖权威源 | 强制（①） | DDD INV-DATA-02 |
| `T-LOCK-001` | 排他锁不得跨越外部 IO | 强制（①） | DDD INV-CONC |
| `T-LOCK-002` | 持锁不得长耗时，异步须在锁释放后 | 强制（①） | DDD INV-CONC |
| `T-TRX-002` | 事务边界不得含外部 IO（见 `T-TRX-001`） | 强制（①） | DDD INV-CONC |
| `T-ADPT-001` | 外部调用必须设超时 | 强制（①） | 组织级标准 |
| `T-ADPT-002` | 每个 Adapter 必须明确 Retry、Failure、Degradation 策略及业务影响；允许结论为"不重试 / 不降级"，但须说明理由 | 强制（①） | DDD INV-CONC |
| `T-Q-001` | 异步任务必须可观测，并必须明确失败与重试策略；允许基于业务语义禁止自动重试 | 强制（①） | SRS NFR |
| `T-CONC-001` | 并发对象必须明确控制策略 | 强制（①） | DDD INV-CONC |
| `T-CONC-002` | 对存在重复提交/重复投递可能且重复执行可能产生重复有效业务结果的入口，必须设计业务幂等或等价防重机制 | 强制（①） | DDD INV-CONC-02 |
| `T-ORM-001` | 数据库唯一约束应可追溯至明确的数据完整性/业务唯一性要求，不应仅因"可能有用"而增加 | 应（偏离须说明理由） | SRS BR / DDD INV |
| `T-ERR-001` | 业务可感知异常不得向终端用户暴露敏感内部实现细节（SQL traceback、token、内部模型、路径等）；内部诊断信息进入受控日志/监控 | 强制（①） | SRS 6.2 |
| `T-OBS-001` | 关键业务动作必须可审计 | 强制（①） | DDD 审计语义 |
| `T-MIG-001` | 历史数据须评估迁移或无迁移理由 | 强制（①） | 第 16.3 |

> **强度说明**：`① 工程强制标准`（违反即不合规）、`② 模板变量`（由项目填写值）、`③ 项目设计决策`（须给出本项目答案，见 0.4）。`应`表示原则性要求，偏离须书面理由。
>
> **核心原则（0.4）**：`T-ADPT-002`、`T-Q-001`、`T-CONC-002` 等条目体现"**强制回答，不强制答案**"——项目必须明确策略，但允许结论为"不重试 / 不降级 / 禁止自动重试"，只要理由充分。
>
> 项目可在此基线基础上**裁剪**（单次 Coding Contract 只引用本次相关的 `T-xxx`），但**不得降低**强制项强度。

### 18.2 与 Coding Contract 的关系
