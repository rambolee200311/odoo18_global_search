# Odoo 工程准则

在设计、实现或评审 Odoo 模块时使用本 skill。完整冻结来源副本见 `references/Odoo_Engineering_Guidelines.md`。

## 术语与权威边界

- 来源指南中的 `SHOULD / SHOULD NOT` 统一表述为“应 / 不应”，表示默认工程建议，不是无条件强制规则。明确的偏离记录与批准要求仍必须遵守。
- **偏离**：有意选择不符合一般工程默认建议的方案。引入额外抽象、非原生技术或基础设施属于需要评估的潜在偏离，不能仅凭名称自动批准。
- **已批准**：由当前项目有权的负责人按项目流程授权，并在对应文档中留下记录。
- **冻结**：文档按自身模板与项目治理流程完成审阅、批准，并有有效的 `Frozen` 状态记录。
- **已基线化**：在计划和追溯中记录已批准文档的准确版本，供下游引用。Draft 不得作为下游基线。

先遵守项目已批准的 SRS、DDD、TDD 和 Coding Contract。若来源工程准则与项目已批准的 TDD 在具体方案上冲突，以该项目 TDD 为实施基线，并将冲突及影响记入 IHR；不得静默执行来源建议，也不得借此改变 SRS / DDD 的冻结语义。偏离不等同于绕过项目审批。

本 skill 只指导工程方案选择，不授权开始实施或绕过项目门禁。若项目同时使用 `odoo-project-workflow`，工程偏离仍须遵循该 skill 的 TDD、CC、Implementation Plan 门禁和豁免规则；本 skill 不创建 CC，也不授予测试豁免。

## 来源核对

使用内置指南前，在项目仓库根目录运行：

```bash
python3 docs/skill/odoo-engineering/scripts/check_guideline_sync.py
```

脚本失败时，停止使用内置副本创建或修改权威文档，也不得用旧副本顶替。报告来源差异并停止依赖该副本；阻塞解除前只能准备明确标为 `Draft` 的分析。指南负责人负责确认或修订权威来源；skill 维护者负责按确认后的来源更新内置副本、元数据和必要的校验基线，再运行同步检查。不得只更新校验基线来掩盖未审阅的来源变化。

## 方案选择顺序

对每项需求先确认已批准语义和约束，再依次评估：

1. Odoo 原生能力；
2. 简单的 Model / View / Python；
3. Odoo 官方扩展机制；
4. 必要且成熟的第三方组件；
5. 自研额外技术。

**终止条件：**一旦某层方案有证据证明能稳健满足已批准要求，就停止评估更低优先级的方案，不为比较技术而继续加层。第 5 层只是评估顺序，不代表自动获准；是否偏离及其记录、批准要求统一按“偏离评估与审批”执行。

第三方组件只有同时满足以下条件才可称为“成熟”：持续维护、有适用 Odoo / Python 版本的兼容记录，并有可信社区或官方支持。任一条件无法核实时，不按成熟组件直接引入；退回 Odoo 原生、自研或其他方案评估，并按偏离规则记录证据与风险。

## Odoo 实现准则

### Model：简单、符合 ORM 习惯

优先标准 Field、关系字段、Related、Compute、Constraint、标准 ORM Method 和清晰的 Business Action。Repository、DAO、DTO、Mapper、Entity Wrapper、Generic Engine、自建 ORM 或额外 Persistence Layer 只有在有具体收益时才考虑；可验证的收益包括跨模块复用、外部系统隔离、可测试性显著改善，或解决标准 ORM 无法满足的明确约束。仅为了分层、命名习惯或少量重复代码，不构成真实收益。

### View：先用标准界面能力

优先 Form、List、Search、Kanban、Wizard、Domain、Context、Modifier、Standard Widget 和 View Inheritance。标准 XML View 能满足需求时，不引入自定义 Owl / JavaScript / Widget。确有必要时，先在 TDD 记录原因、影响、替代方案和验证方式，并按项目流程获得批准。

避免复杂 XPath、多层脆弱继承、复制整个官方 View、大量动态 UI 逻辑，以及依赖 UI 隐藏核心正确性规则。

### 业务逻辑：显式且可追踪

核心业务规则放在 Model / Business Action 中。Context 只传递调用参数，不承载业务状态或隐藏关键业务事实。避免隐式副作用、在 Compute 中执行复杂业务动作、在 View 中实现核心业务规则，或用技巧隐藏实际执行路径。

### 稳健优先于技巧

优先选择清晰、可预测、易测试、易排错、易升级和易维护的实现。避免无必要的元编程、Monkey Patch、Runtime Method Replacement、复杂 Decorator、过度通用化和难理解的动态代码。若确需采用其中任一做法，必须在 IHR 记录原因、作用范围和回退方案；按项目约定同时更新 TDD / CC。

### 避免过早抽象

少量清晰的重复代码可以优于错误抽象。作为评估提示：相同逻辑在三个或更多真实场景重复出现，且语义、变化原因和接口已稳定时，再考虑抽象；“出现三次”只是评估触发点，不自动证明抽象合理。可以拆方法，不轻易造框架。

### 控制额外技术

能够由 Odoo 原生能力稳健完成时，不无故引入 Redis、Kafka、RabbitMQ、Celery、独立 Worker、微服务、Elasticsearch、独立缓存层、Event Bus、CQRS、Event Sourcing、自建前端框架或大型第三方依赖。引入任何额外技术前，必须在 TDD 记录所解决的问题、选型、已评估的原生及其他替代方案、证据和验证结果，并按项目流程批准后再实施。

### 验证真实 Odoo 行为

Mock 只用于单元层的隔离验证；不得用 Mock、快捷实现或辅助脚本代替关键路径的真实行为验证。关键路径由 TDD 指定；若 TDD 尚未指定，应在 TDD / CC 中明确。关键路径应尽可能经过真实 ORM、Business Action、用户权限、模块依赖、Odoo Runtime 和升级路径。

## 偏离评估与审批

偏离必须在实施前同时具备以下三项，缺一不可：

1. **已记录的具体问题**：说明当前方案无法满足的需求、约束或风险，不接受笼统的“更灵活 / 更先进”。
2. **已评估的原生方案**：列出适用的 Odoo 原生能力及为何不足；如果存在可稳健满足需求的原生方案，应停止继续比较并采用该方案。
3. **证据来源**：标明可核验的来源，如真实 Runtime 试验、兼容性或升级限制、性能数据、官方文档，或明确的已批准要求。未经验证的假设不能当作证据。

以下任一情况视为**重大偏离**：改变或试图改变已冻结语义、引入新的运行时基础设施 / 外部服务、改变模块升级或数据迁移路径、跨模块引入共享契约或依赖。若涉及已冻结 SRS / DDD / TDD 语义，不能仅按重大偏离记录后继续；必须停止并先走相应上游变更流程。其他重大偏离至少记录到 TDD，并按影响更新 CC 与 IHR；普通偏离也须在适用的 TDD、CC 或 IHR 留下决定和追溯。

评估时回答并记录：

- 具体问题及受影响的需求 / 约束是什么？
- 已评估哪些 Odoo 原生方案，为什么不足？
- 证据来源、范围和结果是什么？
- 偏离将影响哪些模块、权限、数据、接口、升级路径或测试？
- 选择了什么方案，考虑过哪些替代方案，如何验证和回退？
- 哪些 TDD、CC、IHR 或追溯记录需要更新？

回答必须落入适用的项目文档（TDD / CC / IHR），仅口头说明不算记录。偏离要生效，必须由有权的人按对应文档的批准流程授权；完成记录本身不代表已批准。偏离未经批准前，停止受影响实现。实际实施超出已批准范围时，停止并重新评估、记录和授权，不得事后补写成已批准。

## 默认决策原则

方案冲突时按以下顺序取舍：**先满足已批准要求，其次保证稳健，再在可稳健满足要求的方案中选最简单的实现**；同时兼顾可测试、易升级和易维护。

**已批准要求 → 稳健满足 → 最简单方案 → 可测试 / 易升级 / 易维护**
