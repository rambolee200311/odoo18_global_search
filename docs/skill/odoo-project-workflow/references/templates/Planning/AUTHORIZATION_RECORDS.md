# 人工授权记录

本文件定义两类必须由可识别的人类授权并写入项目文档的记录。Agent 只能检查记录完整性和执行流程门禁，不得代替授权人判断测试可忽略或 TDD 可偏移。

授权人必须是当前项目已知的负责人、维护者或明确指派的批准人，并能对应到具体自然人；匿名身份、仅写角色名（如“团队”）或无法对应到人的标识无效。完整授权记录默认存放在项目级 `docs/implementation/AUTHORIZATION_RECORDS.md`（或项目已规定的受控授权登记册）；本 skill 中的本文件仅为格式模板。

## 1. 统一工作流证据状态

每条测试、检查、验证场景或覆盖证据必须填写以下 `Workflow Evidence Status` 之一，并保留原模板的原生状态字段：

| Workflow Evidence Status | 含义 / 常见原生状态映射 | 不得写成 |
|---|---|---|
| `Passed` | 原生 `PASS`；FR 的 `SATISFIED`；PVR 有有效证据确认满足 | 无证据的“已测试”或“已完成” |
| `Failed` | 原生 `FAIL`；FR 的 `NOT SATISFIED`；已执行且未满足的验证 | `Passed`、“已测试”或“已完成” |
| `Skipped` | 原生 `SKIPPED`；计划中的验证被跳过 | `Passed`、“已测试”或“已完成” |
| `Blocked` | 原生 `BLOCKED`；被外部条件或未解决问题阻止，当前无法执行 / 判断 | `Passed`、“已测试”或“已完成” |
| `Missing` | 原生 `NOT RUN`、`EVIDENCE MISSING`，或没有可用执行证据 | `Passed`、“已测试”或“已完成” |

适用性状态（如 `N/A`）不是证据状态，应单独标记适用性及理由，不得映射成 `Passed`。`PARTIAL` 等汇总状态必须拆解到具体测试 / 场景后分别填写；不能用汇总状态遮盖失败项。保留来源模板原生字段，例如 `ATR: FAIL` 加 `Workflow Evidence Status: Failed`。

测试豁免只适用于 `Failed / Skipped / Blocked / Missing`。不得因授权而把底层状态改成 `Passed`。若该项是某条 SRS 需求的唯一验证手段，不得豁免；须退回 SRS 负责人，或先补充并执行替代验证。

## 2. 永久测试豁免记录

本节定义永久豁免的记录格式与处理通道；是否启用豁免由人类授权决定，skill 无权决定某个未通过项应否豁免。

豁免必须由人批准并写入项目授权登记册。每份 FR 列出其 CC 范围内的豁免记录 ID；PVR 汇总项目级全部豁免记录 ID。FR / PVR 引用 ID 和登记册路径，不重复抄写完整授权内容。每条记录必须包含以下字段；`授权人` 不能为空：

```text
记录 ID：EXEMPTION-<CC-ID>-<序号>
豁免项：<测试 / 检查项 ID>
状态：<Failed / Skipped / Blocked / Missing>
原因：<为什么现在不处理>
影响：<对需求、数据、上线和后续阶段的影响>
授权人：<项目已知负责人 / 维护者 / 明确指派批准人的姓名及可核验标识>
```

同一 CC 内序号递增且不复用；项目授权登记册是 ID 到完整授权记录的唯一索引。

含豁免的 FR 和 PVR 都必须按对应范围列出记录 ID（FR 为单 CC，PVR 为项目级汇总），并记录：

```text
Freeze disposition: FROZEN WITH OPEN ITEMS
授权登记册：<项目授权登记册路径>
豁免记录 ID：EXEMPTION-<CC-ID>-<序号>（多个 ID 逐项列出）
```

豁免永久接受，不填写有效期或复审条件。原测试 / 检查结果仍保留原状态和原证据；授权只允许文档按 `FROZEN WITH OPEN ITEMS` 冻结，不把结果改写为通过，也不自动将 FR Closure Status 或 PCR Project Closure Status 改为满足。PCR 按其既有规则评估 FR / PVR 的状态和风险。

若有未通过项但缺少完整记录、有效授权人或操作者明确确认“已获授权”，默认阻止冻结。Agent 不得自行判断某项测试可以忽略，不得推断、补写或冒充授权。

## 3. TDD 偏移授权与反向更新记录

本节定义 TDD 偏移的授权通道与记录格式；是否启用偏移由人类授权决定，skill 无权自行批准偏移。

发现实现需要偏离当前冻结 TDD 时，默认立即暂停受影响的 CC 和实现。继续前，必须由人批准并记录：

```text
记录 ID：OFFSET-<CC-ID>-<序号>
偏移项：<TDD 条款 / 约束 ID>
原 TDD 版本：<当前冻结版本>
实际实施：<授权前填写拟实施的偏离方案；完成后更新为实际实施内容>
偏移原因：<为什么必须偏离>
影响：<对需求、数据、接口、权限、测试和后续阶段的影响>
授权人：<项目已知负责人 / 维护者 / 明确指派批准人的姓名及可核验标识>
反向生成 TDD 版本：<目标新版本号；授权前确定，完成后填写实际路径 / 版本>
```

授权记录必须在恢复受影响工作前完整；授权人、目标版本或上述其他必填内容缺失时继续保持 `BLOCKED`。目标 TDD 版本须遵循项目版本规则；项目没有版本规则时，先由负责人确定，不由 Agent 猜测。CC、IHR、ATR、HVR、FR 及适用的 PVR / PCR 引用偏移记录 ID 和登记册路径。

同一 CC 内偏移序号递增且不复用；项目授权登记册是 ID 到完整授权记录的唯一索引。

恢复工作前，“实际实施”栏记录人类批准的拟实施方案和偏移边界；实施完成后，必须更新为实际实施事实并关联 CC / IHR 证据。实际实施与获批方案不一致时，立即停止受影响工作并重新取得授权；禁止事后补写或改写记录使两者看似一致。

偏移实施完成后，必须根据实际实施另存并反向生成新版本 TDD：

- 使用独立的新版本文件 / 记录；版本号递增。
- 旧冻结 TDD 不覆盖、不删除；按项目约定归档并保持可查。
- 新 TDD 按 `references/templates/Designing/TDD模板.md` §0.5 的冻结与变更规则完成评审、批准和冻结，成为新的当前基线。
- 更新 Implementation Plan 的 TDD 基线、影响分析和阶段 / CC 映射；新 CC 使用新 TDD 版本。
- CC、IHR、ATR、HVR、FR（以及适用的 PVR / PCR）逐份标明自己实际依据的 TDD 版本。历史文档不改写为新版本；受影响文档补充偏移 ID 和新 TDD 反向更新引用。
- 反向更新 TDD 完成、批准并冻结前，不得关闭受影响的 CC / FR，不得将计划的基线有效性恢复为 `VALID`。

人工批准的偏移只授权所记录的偏移范围，不自动批准其他偏移，也不代表验证通过。

若同一变更既需要 TDD 偏移又涉及测试豁免，先完成偏移授权、实施、反向生成并冻结新版本 TDD、更新基线，再按新 TDD 重新执行和评估相关验证。不得沿用偏移前的豁免结论；这是新技术基线带来的影响评估，不是豁免有效期或定期复审。原记录仍作为其原证据 / 基线下的永久授权保留。

## 4. SRS 不可由本流程修改

- 不得因 TDD 偏移或实际实现而修改、重写或反向生成 SRS。
- 如果偏移触及 SRS 的业务含义、需求、验收标准或业务状态，立即停止受影响工作及对应 CC 的 FR / PVR 冻结，并将问题交回 SRS 负责人处理。
- 不得用 TDD 偏移、新版本 TDD、测试豁免或 Implementation Plan 变更绕过 SRS 权威。批准的业务需求基线在本流程中保持不变。

## 5. 两类人工授权的区别

| | 测试豁免 | TDD 偏移 |
|---|---|---|
| 对象 | 测试 / 检查项 | 冻结 TDD 条款 |
| 人工授权 | 强制，记录可识别授权人 | 强制，记录可识别授权人 |
| 结果 | 接受未通过状态，永久有效；FR/PVR 标记 `FROZEN WITH OPEN ITEMS` | 暂准所记录的实施偏移；完成后反向生成并冻结新版本 TDD |
| 是否产生新基线 | 否 | 是；新版本另存，旧版本保留并归档 |
