## 1. 目的与验证原则

### 1.1 目的

在进入 M1 TDD 前，通过隔离、可重复、可追溯的实测，确认候选组件处理 SRS 范围内 `.xlsx`、`.docx`、`.xls`、`.doc` 的能力与限制，尤其是旧版格式转换、公式及复杂对象保留、资源消耗和恶意/损坏输入的失败方式。验证结论用于 TDD 的技术决策和 SRS 未决项关闭，不直接构成实现方案或实现授权。

### 1.2 原则

1. **拒绝盲猜：** 每项结论必须有可复现的独立脚本、输入样本标识、运行环境、原始输出和判定依据。
2. **先测高风险样本：** 优先测试业务中结构复杂、历史兼容性差或包含多种对象的样本；不以简单演示文件替代极端样本。
3. **隔离运行：** 测试不访问 Odoo ORM、业务数据库、生产附件或外部业务 API。每个解析器/转换作业在独立临时目录运行，清理策略和超时明确。
4. **不执行活动内容：** 不运行宏、脚本、嵌入式对象或外部链接内容；宏样本仅用于验证识别、转换及拒绝边界。
5. **可追溯、可脱敏：** 样本应获准用于测试并去除真实个人/客户信息。清单记录来源类别、格式、大小、SHA-256 和结构特征，不在仓库提交未经批准的业务文件。
6. **区分验证与设计：** TV 记录事实及不确定性；最终支持范围、降级行为、依赖选择和异步架构由后续 SRS/TDD 评审确定。

### 1.3 结论状态

每一验证项使用以下状态之一，并附证据：

| 状态 | 判定含义 |
|---|---|
| `VERIFIED` | 按本计划完成重复验证，达到预先定义的通过准则，证据可复现 |
| `NOT VERIFIED` | 完成验证但未达到准则，或发现明确不支持/损坏/不安全行为 |
| `INCONCLUSIVE` | 环境、样本或测量不足，不能得出支持或不支持结论 |
| `NOT RUN` | 尚未执行；本计划当前所有验证项均为此状态 |

## 2. 验证范围和边界

### 2.1 范围内

- OOXML 工作簿 `.xlsx` 和文档 `.docx` 的结构读写与回读校验。
- 二进制旧格式 `.xls`、`.doc` 的直接处理能力及 LibreOffice 转换/回转能力。
- 公式文本、缓存值、合并单元格、样式、条件格式、外部链接、图片、页眉页脚、文本框等结构保留情况。
- 大文件解析/写回耗时、峰值内存以及 LibreOffice 多进程并发转换行为。
- 空文件、格式伪装、加密文件、截断/损坏包、异常 XML 和受控压缩炸弹样本的异常与进程稳定性。

### 2.2 范围外

- Odoo 菜单、模型、权限、附件、聊天界面或业务流程开发。
- Skill、AI 映射、提示词质量或 LLM Provider 的验证。
- 生产环境部署、生产文件处理或生产数据读取。
- 执行 Office 宏、外部链接、嵌入对象中的代码。
- 本计划阶段决定具体队列实现（如 `queue_job`）、最终库选型或支持承诺。

## 3. 环境准备

### 3.1 环境记录

执行前创建环境快照，至少记录：

- 操作系统名称/版本、架构、CPU 核数、可用内存、文件系统和临时目录位置。
- Python 可执行文件路径及 `python --version`；在本项目环境中优先使用 `venv/bin/python`，不得误用系统 Python。
- 候选 Python 包的精确版本及依赖清单；记录 `pip freeze` 或等效只读清单。
- LibreOffice `soffice --version` 的完整输出、安装来源和构建信息（若可获取）。
- locale、时区、默认字体清单（可获取时）、磁盘可用空间。视觉版式验证须在与目标业务环境匹配的中文字体条件下执行；记录安装的字体家族、字体文件/软件包版本及字体替代配置。可使用 `fc-list` 等命令留存字体清单。微软雅黑、宋体等字体只有在获得合法许可且与目标环境一致时才使用；若缺少样本所需字体，相关视觉比对标记为 `INCONCLUSIVE`，不得将字体替代导致的差异归因于文档引擎。
- 每次运行的开始/结束时间、命令、退出码、标准输出、标准错误和超时设置。

### 3.2 候选组件（待实测，不代表已选型）

| 组件 | 候选版本/用途 | 验证注意事项 |
|---|---|---|
| `openpyxl` | `3.1.x`，读写 `.xlsx` | 记录精确补丁版本；不用于 `.xls` |
| `python-docx` | `1.1.x`，读写 `.docx` | 记录精确补丁版本；不用于 `.doc` |
| `xlrd` | `2.0.1`，候选 `.xls` 值读取器 | 仅用于 `.xls` 读取探底；记录其读取值/公式表现，不期待它保留或重写复杂样式；不用于 `.xlsx` |
| `xlrd`（可选对照） | `1.2.0`，仅在依赖与安全评估允许时测试 | 作为旧版兼容性对照，不预设其能解决 `.xls` 样式保留问题；单独记录安装、安全维护和解析结果 |
| `xlwt` | `1.3.0`，候选 `.xls` 写入器 | 单独评估旧格式写入和样式能力；不得假设可无损修改既有工作簿或往返 |
| LibreOffice | 环境提供的 Headless `soffice` | 记录精确版本；每个并发作业使用隔离用户配置目录 |
| `psutil` | 峰值 RSS/进程树采样 | 精确记录版本；同时采样 LibreOffice 子进程 |
| Python 标准库 | `zipfile`、`xml.etree.ElementTree`、`subprocess`、`time`、`hashlib` 等 | 用于结构检查、进程隔离和证据生成 |

版本号是候选范围，不作为已验证依赖锁定。正式执行前应确认可安装性、精确版本及许可证/分发约束，并将实际环境快照纳入报告。

### 3.3 隔离与运行控制

- 每个样本复制到唯一临时工作目录，原件只读保存并计算 SHA-256；输出文件单独存放。
- 每个解析/转换用独立子进程执行，设置墙钟超时、内存/CPU 监控和退出码采集。超时后终止进程组并记录是否留下孤儿进程。
- LibreOffice 每个作业使用独立 `UserInstallation` profile 和独立输出目录，避免共享 profile 锁；并发时禁止复用同一 profile。并发测试前后及每个任务结束时采集进程列表（如 `ps -eo pid,ppid,stat,etime,cmd`），检查残留 `soffice.bin`/`soffice` 进程、profile 锁文件及输出目录串写；记录残留进程 PID、父 PID、状态和清理结果。
- 禁止从压缩包解压到测试根目录之外；禁止访问网络；不自动打开生成的文件。
- 对压缩包样本设置输入大小、条目数、单项解压大小和总解压大小上限。测试脚本不得调用无界的 `extractall()` 或一次性读取完整解压内容；先检查 ZIP 元数据，再以分块、有累计上限的方式读取，超过单项/总膨胀限额即停止。该限制不替代进程级资源保护：解析须放在可强制终止的独立子进程中，并设置内存/CPU/墙钟上限；可使用操作系统资源限制、容器限制或监控到阈值后终止子进程。压缩炸弹使用小型受控样本，不在共享/生产主机制造高资源消耗。

### 3.4 样本集设计与登记

建立只含元数据的 `sample_manifest.csv`，字段建议包括：`sample_id`、格式、字节数、SHA-256、来源类别（合成/授权脱敏业务样本）、复杂特征、预期检查项、宏/外链/加密标记、许可状态。样本文件本身默认不提交 Git。

| 样本组 | 必备结构 |
|---|---|
| `.xls` 旧式工作簿 | 公式、合并单元格、非默认数字格式/样式、隐藏工作表、打印设置；另备含宏或宏相关内容的样本，仅验证不执行和格式边界 |
| `.doc` 旧式文档 | 段落、表格、页眉页脚、分页/版式、图片、字段；至少一个包含文本框/VML/浮动对象的样本 |
| `.xlsx` 现代工作簿 | `=SUM(A1:A10)`、合并单元格、条件格式、外部链接、图片、命名区域、数据验证、不同样式及公式缓存值 |
| `.docx` 现代文档 | 段落、表格、图片、页眉页脚、分页/节、超链接；尽可能包含 DrawingML/VML 文本框和浮动对象 |
| 大文件 | 约 50,000 行工作簿；约 10 MB 文档；另记录实际行数、ZIP 解压后大小、图片数及对象数 |
| 异常/安全样本 | 空文件、随机脚本字节伪装 `.xlsx`、错误扩展名、截断 ZIP、无效 OOXML/XML、加密 Office 文件、受控高压缩比 ZIP |

对于每种格式至少准备一个可控合成样本和一个经授权脱敏的真实业务样本（若无法取得真实样本，标记样本覆盖缺口并将结论降为 `INCONCLUSIVE`）。样本必须在运行前定义待比较属性，避免看过结果后调整通过标准。

## 4. 验证矩阵与执行方法

### 4.1 维度一：旧版 `.xls` / `.doc` 读写与转换

**编号：** `TV-OFFICE-M1-01`
**问题：** 候选 Python 库能否直接处理旧格式？LibreOffice 转换和回转是否满足 SRS 的格式、结构及版式要求？

#### 测试步骤

1. 对 `.xls` 样本分别用 `openpyxl.load_workbook()` 尝试打开并记录异常类、消息、退出码；对 `.doc` 样本用 `python-docx.Document()` 尝试打开并记录同类信息。不得将预期失败写成实测结果。
2. 用候选旧版库读取 `.xls`（如 `xlrd 2.0.1`），登记可读取的工作表、单元格值、公式呈现方式、合并区域、可访问的格式信息和无法访问的对象。`xlrd` 在此作为值读取探底工具，不将其视为样式保留工具。可选地在依赖/安全评估允许时增加 `xlrd 1.2.0` 对照；单独评估 `xlwt` 写入能力，并明确它能否修改既有文件及其样式损失，不假设 `xlrd + xlwt` 可以无损往返。若业务要求修改后保留旧版样式，重点判断是否应改用 LibreOffice 转换/回写或对旧格式施加经 SRS 批准的限制。
3. 用 LibreOffice Headless 将 `.xls` 转为 `.xlsx`、`.doc` 转为 `.docx`。记录命令、耗时、退出码、stderr、输出文件可重新打开情况及转换警告。
4. 对转换前后执行结构比较：
   - `.xls/.xlsx`：公式单元格及表达式、合并范围、工作表名称/顺序、单元格值、样式/数字格式、行列隐藏状态、页面设置、图片/对象（如适用）。
   - `.doc/.docx`：段落/表格数量和文本、页面/节设置、页眉页脚、图片、文本框/浮动对象、分页相关结构。
5. 将 `.xls -> .xlsx` 后的工作簿按 SRS 期望路径修改并保存，再用 LibreOffice 转回 `.xls`。检查公式、合并区域、关键样式和文件可打开性是否损坏。`.doc` 转换回旧格式如工具支持，也执行同等往返比较；不支持时记录为边界，不伪造结果。
6. 对复杂旧版 Word/Excel 样本生成转换前后可视化证据：优先由 LibreOffice 导出 PDF，再渲染页面图；以人工复核加可复现的图像差异指标记录偏移、缺失、换页和对象丢失。运行前核对目标中文字体已安装且被 LibreOffice 识别，避免方框字或字体回退污染版式结论。图像差异阈值需在报告中说明，不能单独以像素相似度代替结构检查。

#### 指标与通过判定

- 转换成功率：成功输出且能重新打开的样本数 / 执行样本数，按格式和方向分开报告。
- 属性保留率：对预先登记的属性逐项判定保留/丢失/改变/无法判断；同时报告分子分母，不以单一总体百分比掩盖关键对象损坏。
- 记录公式、合并区域、关键样式和文本框的精确差异；公式/业务文本丢失属于关键失败，即使文件可打开也不得记为完全成功。
- 转换耗时单独记录输入、转换和输出验证阶段；至少重复 3 次，报告每次值、中位数和最大值。
- 若旧格式转换出现严重或结构相关的保真问题，报告必须提出可验证的旧版结构支持白名单/拒绝边界候选（例如按公式、文本框、对象或版式特征划分），并给出样本证据；该候选不自动改变冻结 SRS，超出当前需求承诺的限制须经 SRS 变更批准。

#### 预期风险（待验证）

- 直接 Python 库无法读写旧二进制格式，或读写能力只覆盖有限结构。
- LibreOffice 转换可能改变字体、页边距、分页、公式兼容性或对象布局；回转可能进一步丢失旧格式特性。
- 文本框、VML、嵌入对象、特殊打印设置可能无法稳定往返。

#### 产出

- `TV_Office_Engine_M1_Report.md` 中旧格式章节。
- `TV_Office_Engine_M1_Conversion_Matrix.csv`：方向、样本、成功状态、耗时、警告、关键差异。
- `TV_Office_Engine_M1_Style_Diff.csv`：预登记样式/版式属性的前后状态。
- 经脱敏的转换日志、PDF/PNG 对照证据及 SHA-256 清单。

### 4.2 维度二：现代 `.xlsx` / `.docx` 结构保留和回读校验

**编号：** `TV-OFFICE-M1-02`
**问题：** Python 库修改允许字段时，公式、OOXML 结构及复杂 Word 对象是否保留？有哪些可在无 Excel/Word GUI 环境下执行的后端校验？

#### Excel 测试步骤

1. 对 `.xlsx` 基线样本记录公式单元格坐标和公式文本、`data_only=False` 读取结果、`data_only=True` 读取结果、合并范围、条件格式规则数、外部链接、图片、命名区域、数据验证及关键样式。
2. 使用 `openpyxl` 仅修改一个预先指定的非公式单元格并保存到新文件；不使用 `data_only=True` 作为写入模式。
3. 重新以 `data_only=False` 打开，逐个比较公式坐标与公式文本；另以 `data_only=True` 打开，记录公式缓存值是否存在、是否改变或变空。特别核实 `openpyxl` 保存前后缓存值的行为；若保存后缓存值丢失或失效，明确报告该结果，不得假设下载端会自动计算。公式文本和计算缓存必须分开报告。
4. 若发现缓存值丢失/失效，继续评估 LibreOffice Headless 对最终文件的公式重算和保存能力：对含已知答案的受控公式样本，先确认公式文本未损坏，再由 LibreOffice 打开/重算/保存，重新以 `data_only=True` 检查缓存值，并以独立计算结果核对。记录重算耗时、公式兼容性警告和其它 OOXML 结构差异。该步骤只验证候选补救能力，不预先决定生产方案；TDD 必须明确是否引入重算步骤及其格式风险，不能把“用户下载后按 F9”当作既定补救行为，除非经需求变更明确接受。
5. 对 ZIP/OOXML 做结构回读：安全枚举包内条目；解析 workbook、worksheet、styles、relationships、shared strings、external links、drawing、conditional formatting 相关 XML。按语义比较公式 `<f>`、公式所在单元格、合并 `<mergeCell ref>`、工作表关系、定义名称、条件格式、图片关系和样式引用。XML 属性顺序/无关序列化差异做规范化后再比对；同时保存必要的原始 XML 片段证据。
6. 计算公式结构摘要（工作表名、单元格坐标、公式文本）及合并区域摘要的哈希；比较修改前后摘要。除非另有验证，不把二进制文件整体哈希相同作为通过要求。
7. 对外部链接采取只检查关系和引用的方式，不触发链接更新或网络访问；检查保存后链接条目/关系是否保留。

#### Word 测试步骤

1. 使用 `python-docx` 修改一个普通段落或表格单元格，保存新副本。
2. 对比包内 `word/document.xml`、header/footer、relationships、media 清单；统计并核对段落、表格、图片引用、节、页眉页脚及文档文本。
3. 对文本框/浮动对象重点检查 DrawingML/VML 节点及其中的文本。保存前后提取对应 XML 节点数量、文本内容和关系目标，确认是否存在库未暴露但保存时静默丢弃的结构。
4. 对修改前后文档分别由 LibreOffice 导出 PDF/PNG 作为可视化复核证据；记录版式变化，但不把 LibreOffice 渲染作为 `python-docx` 保留 OOXML 的唯一证据。

#### 判定与输出

- 必须分别报告“常规结构可修改并保留”“结构能打开但有损”“不支持/发生对象丢失”“无法判断”四类。
- 公式文本保持与公式缓存保持是两个独立结果；不得因公式字符串仍在就声称计算值已更新。
- 生成 `TV_Office_Engine_M1_Structure_Diff.csv`，列出对象类型、原数量/内容摘要、新数量/内容摘要、结论、证据位置。
- 生成 `TV_Office_Engine_M1_Formula_Check.json`，列出样本、公式摘要、修改前后缓存状态、结果；不得包含敏感单元格业务值。

#### 预期风险（待验证）

- `openpyxl` 保存可能重写 OOXML 部分结构；外部链接、图表/绘图、扩展对象或公式缓存可能改变。
- `python-docx` 对部分高级 OOXML（尤其文本框、VML/浮动布局）缺少高层 API；是否在保存时丢弃必须实测。
- 单靠库级对象模型无法证明文件整体未损坏，因此需结合 XML 结构检查和重新打开测试。

### 4.3 维度三：性能与并发压力

**编号：** `TV-OFFICE-M1-03`
**问题：** 大型文件读、写、转换的耗时及峰值资源是否适合 Odoo 同步 HTTP 请求？LibreOffice 并发是否稳定？

#### 测试步骤

1. 使用约 50,000 行 `.xlsx` 和约 10 MB `.docx`，同时记录实际文件大小、解压后大小、工作表/段落/表格/图片数量等复杂度指标。
2. 将处理阶段拆分计时：文件读取、结构解析、修改、保存、重新打开/校验、LibreOffice 转换。每类场景先进行 1 次预热，再至少执行 10 次；若需报告 P95，则将样本次数提高到至少 30 次。
3. 以独立进程采样 Python 和 LibreOffice 进程树峰值 RSS；记录峰值内存、CPU 时间、墙钟时间、退出码、输出大小及失败数。区分冷启动和进程复用（如适用）。
4. LibreOffice 转换并发按 1、2、4 个作业逐级进行；每个任务独立临时目录和独立 profile。记录吞吐、延迟、profile 锁冲突、异常退出、超时、挂起、遗留进程和输出文件串写/覆盖；每轮开始前、每个任务结束后及整轮结束后采集进程列表，核查是否残留 `soffice.bin`/`soffice` 进程，并记录 PID、父 PID、状态、运行时长和是否成功清理。确认使用独立 `UserInstallation` 时是否仍发生文件锁竞争。
5. 每种并发档至少重复 3 轮；出现超时/挂起时收集进程状态和日志，再清理整个进程组。不得无限增加并发或在共享机器造成资源耗尽。
6. 将实测耗时和内存与目标 Odoo 实例的 HTTP 超时、Worker 内存限额及可用 Worker 数进行对照。对照值必须从 `odoo.conf`/运行环境读取并在报告记录；TV 本身不修改服务配置。

#### 判定与输出

- 性能报告提供每次数据、中位数、最大值；样本量足够时提供 P95。不能只报告平均值。
- 明确给出 `同步候选`、`需要异步处理` 或 `证据不足` 的结论，并说明所依据的超时/内存预算和安全余量。
- 若实测最坏/高分位耗时接近或超过实际请求预算，或峰值 RSS 可能突破 Worker 限额，应将异步执行列为 TDD 必须解决的需求；是否采用 `queue_job`、轮询或其他方式留给 TDD 决策。
- 若并发出现死锁、profile 锁或输出串写，则不能把当前并发方案判为可用；需验证隔离 profile/限并发后再关闭问题。

#### 产出

- `TV_Office_Engine_M1_Performance.csv`：操作、样本、轮次、耗时、RSS、CPU、输出大小、退出状态。
- `TV_Office_Engine_M1_Concurrency.csv`：并发度、运行轮次、成功/失败/超时、锁冲突、吞吐和资源数据。
- 报告中的异步必要性结论及其测量依据；此结论不预选队列产品。

### 4.4 维度四：安全与格式伪装

**编号：** `TV-OFFICE-M1-04`
**问题：** 候选解析器遇到格式伪装、加密、空文件、损坏包和高压缩比输入时，是产生可控异常还是导致进程崩溃/挂起？

#### 测试步骤

1. 准备以下受控样本：零字节文件；随机文本/脚本字节但扩展名为 `.xlsx`；扩展名与 MIME/文件签名不匹配；截断 ZIP；合法 ZIP 但缺少必需 OOXML 部件；畸形 XML；加密 Office 文件；受限体积的小型高压缩比 ZIP。
2. 通过目标库和 LibreOffice 的独立子进程分别尝试识别/打开；只记录解析行为，不执行其中内容，不解压到不受控路径，不访问外部链接。压缩炸弹/高压缩比样本必须由测试脚本进行限额读取：先检查元数据，再用分块读取并在达到单项或总解压字节上限时立即停止；绝不直接无界 `extractall()` 或完整载入内存。即使启用限额读取，也必须在可超时、可强制终止且设有内存上限的子进程中运行，并记录触发限额/终止的原因。
3. 记录异常类型、异常消息脱敏摘要、进程退出码/信号、耗时、峰值 RSS、是否超时、是否产生部分输出、临时目录是否可清理。
4. 检查压缩包条目路径是否包含绝对路径或 `..`，并验证测试工具只做安全枚举，不将条目内容解压到目标目录之外；记录 ZIP 声明的压缩/未压缩大小与实际限额读取字节数，验证元数据异常或膨胀超限时能停止处理。
5. 对每一种失败类型验证“拒绝输入”是否可被上层稳定识别；本 TV 不开发 Odoo 拦截逻辑，只形成解析边界和策略要求。

#### 判定与输出

- 区分“可捕获格式异常”“库返回明确不支持”“非零退出/信号崩溃”“超时/挂起”“资源超限”五类。
- 不以捕获到 Python 异常就宣称安全；还需确认进程资源受控、输出未被误当成有效文件。
- 建议的后续拦截策略至少评估：文件大小上限、扩展名与 MIME/签名/容器结构联合校验、ZIP 条目及膨胀限制、加密文件拒绝、解析子进程超时/资源限制、失败时清理临时文件、宏与外链不执行。
- 如任一候选解析器可被受控样本稳定打崩或挂起，必须将进程隔离及资源限制列为 TDD 安全门禁；无法可靠限制时不得将该解析器纳入生产路径。

#### 产出

- `TV_Office_Engine_M1_Security_Matrix.csv`：输入类型、候选工具、异常/退出状态、耗时、峰值 RSS、输出状态、结论。
- 脱敏日志和样本 SHA-256 清单；不提交恶意载荷本身，除非仓库安全评审明确允许。

## 8. 风险阻断与 TDD 决策输入

| 验证失败/不确定情形 | M1 TDD 阶段的强制处理 |
|---|---|
| `.xls` 或 `.doc` 代表性样本不能满足预期读写/转换保真 | 不得静默宣称支持或直接从 SRS 删除；明确失败结构与样本覆盖，验证替代方案。若无法满足冻结 SRS，发起 SRS 变更评审，批准前该格式保持未验证/阻断状态。 |
| LibreOffice 转换或回转导致关键公式、字段文本、合并区域、文本框或版式损坏 | 不将该转换路径作为可用生产路径；验证替代引擎或限定可支持边界。若边界改变业务承诺，先走 SRS 变更。 |
| 公式文本保留但缓存值被清空或过期 | 分别报告表达式保留和计算结果状态；不得声称公式已重新计算。TDD 明确是否只保证公式表达式及是否需要独立重算能力；如与 SRS 验收冲突，提交需求决策。 |
| `python-docx` 保存丢失文本框、浮动对象、图片关系或高级 OOXML | 该对象类别标记为不支持/有损；若属于冻结需求必需范围，阻断对应设计并评估替代方案或 SRS 变更。 |
| 性能耗时超过目标请求预算，或峰值 RSS 威胁 Worker 稳定 | 将异步执行、并发限制、文件大小边界和资源隔离列为 TDD 必答项；根据测量决定机制，不在 TV 阶段指定 `queue_job`。 |
| LibreOffice 并发死锁、profile 冲突、串写或孤儿进程 | 当前并发方式判失败；需验证独立 profile、独立临时目录、任务限流和进程清理后再作为候选。 |
| 异常文件导致解析器崩溃、挂起或资源失控 | 要求隔离子进程、超时、资源限制和严格格式校验；无法可靠约束时禁止该解析器进入生产路径。 |
| 样本不足、依赖版本不确定、环境与目标服务器差异过大 | 标记 `INCONCLUSIVE`，不得据此冻结相关 TDD 选择；补齐样本/目标环境证据后重测。 |

TV 的结果不能授权超出冻结 SRS 的功能，也不能把失败样本隐藏在总体成功率中。对每一格式和关键结构分别给出可支持边界。

## 9. 执行顺序与完成门槛

建议执行顺序：

1. 冻结样本 manifest、环境快照格式和预登记检查属性。
