## 1. 背景与目标

数据填充和用户连续修改 Office 文件是 M2 的原始产品需求。本 TV 不把它们定义为新增需求；验证不同技术路线能否在既有 Odoo 权限、用户确认、文件验证和交付边界内实现这些目标。

职责边界（作为本 TV 的设计前提，不代表实现已完成）：本地 Office Engine 只负责首轮 Odoo 数据填充；首轮后 Excel 内容编辑由 LLM 主导的受控文件编辑环境完成。后续补充/刷新 Odoo 数据时，本地 Data Tool 仅按当前用户 ORM 权限查询并返回 JSON，不选择 Excel 单元格、不执行文件编辑；LLM 将 JSON 应用于当前工作簿。本地继续负责权限、安全、版本、确认、独立验证和交付。

本 TV 要回答：

1. 当前本地首轮填充及已有支持的 Canonical Operation/Expression 能力是什么，其文件行为如何作为 Candidate A 对照基线记录？Candidate A 不代表后续编辑的目标路线。
2. 当前已配置 Provider `gpt-5.6-luna` 是否具备可用的、适合 Excel 的受控文件编辑能力？若无可用接口，记为 `BLOCKED/NOT SUPPORTED`，不假定 Provider 存在未验证能力。
3. 一个与 Odoo 服务隔离的受控文件编辑环境是否能支持未预先穷举的多轮 Excel 修改，并保住安全、格式、公式和版本要求？
4. LLM 修改后的文件如何被独立验证、用户确认、保存和交付？
5. 文件经过用户编辑后，Data Tool 能否返回身份、业务键、快照范围和完整性明确的授权 JSON；LLM 能否把它应用到当前工作簿并保留既有修改？这是单独的关键能力，不能由普通文件编辑成功推断。

TV 只产出证据和路线比较建议。不得据此自动改写冻结 SRS/TDD/Plan、创建 CC 或编码。

## 2. 原则与边界

1. 当前 TV 基线遵守既有 `TV_office_engine_m2_plan.md`：真实 Provider 调用仅能使用已配置 OpenAI Provider 和 `gpt-5.6-luna`；切换模型/Provider 需另行批准。
2. 未获数据使用批准前，只把合成工作簿/合成业务值发送 Provider。合成数据结果不能替代真实 Odoo ACL/Retriever 集成验证。
3. Odoo 业务读取始终通过当前用户 ORM、ACL 与 Record Rules；不能把 Odoo 凭据、数据库、任意文件路径或服务器工具交给模型/编辑沙箱。
4. 不得在 Odoo 服务进程执行模型生成的任意 Python 或其他任意代码。若候选方式需要执行代码，只能另行设计并批准隔离、短生命周期、资源受限、最小文件输入/输出的环境；本 TV 不批准部署该环境。
5. 不预设 XML Patch、Python、完整 XML 替换、Provider 原生文件 API或其他具体实现为最终方案。用候选方法对照实测。
6. 文件执行结果由独立验证者回读；模型的文字回复、API 的 success 标记和附件记录本身都不能证明用户要求已完成。
7. 公式文本与公式计算结果分开核验。读取到公式文本不得称为公式重算。
8. 保留本地路径作为对照基线；TV 不删除/停用现有 Document Operations 或 M2 本地渲染。
9. 本地 Office Engine 的文件填充限定于首轮。Data Tool 的输出是有范围和来源信息的 JSON，不得包含 Excel 单元格坐标或指令，也不得执行第二轮文件编辑；刷新 JSON 写入当前工作簿属于 LLM 的编辑职责。
10. 对有覆盖、公式替换或结构变化等需用户决策的风险，必须先呈现候选操作的明确目标与预期影响并获得有效确认，之后才执行该风险编辑。候选生成后，本地独立验证实际 Effect、非目标差异和文件完整性；模型陈述或工具成功消息不替代验证。

## 3. 待比较的候选路线

### Candidate A — 本地结构化操作基线

现有本地 Office Engine / Canonical Operation / Mapping 能力仅作为当前能力比较基线，用于记录首轮填充及既有编辑功能的实际覆盖范围、成本和文件行为。Candidate A 不是首轮之后文件编辑的目标架构，也不能因其基线测试结果而推定满足开放式多轮编辑要求。

### Candidate B — Provider 侧受控文件编辑能力（若当前 Provider 有）

通过当前配置 Provider 实际可用且经批准的文件编辑接口操作上传的工作簿；Provider 返回候选文件，Odoo 不执行模型生成代码。TV 首先确认接口存在、支持的 MIME/文件大小/多轮行为、回传字节及可审计请求身份。不存在时记为 `NOT SUPPORTED` 或 `BLOCKED`，不使用未经批准的另一个 Provider 兜底。

### Candidate C — 隔离的受控文件编辑环境

模型通过显式工具契约请求对一个短生命周期受限工作目录中的指定 Office 文件进行编辑；编辑在隔离环境/适配服务执行，只有文件输入和候选文件输出可以跨边界。是否采用成熟库、工具调用或其他机制由经授权的原型比较。该环境必须无 Odoo ORM 凭据、无必要外网、资源受限、每次任务可清理并有审计日志。任何模型生成的代码不得进入 Odoo 进程。本 TV 计划本身不授权构建、部署或运行 Candidate C 原型；Candidate C 原型必须另行取得明确授权，设计评估、计划批准或 Candidate B 的证据均不能代替该授权或原型执行证据。

## 5. 测试材料与记录格式

### 5.1 合成工作簿夹具

使用结构中性的 `.xlsx`，不使用客户/业务专用模板作为单元测试金标。夹具建议覆盖：多工作表、普通表头/数据行、零值、False、空值、日期、数字格式、带公式单元格、合并区域、样式/条件格式、表格/命名区域（若测试目标支持）。记录每个结构项是否在候选方式的支持范围；未知或不支持结构必须显式拒绝或标为不支持，不能静默丢失。

在夹具中设置：

- 可修改目标和用户原话清单；
- 非目标保护区（值、公式、格式、结构）；
- 至少两行有稳定 synthetic row key 的记录，用于排序及刷新身份检查；
- 初始值与目标值，包括 `None`、`False`、`""`、`0`、`0.0` 和日期；
- 文件 SHA-256、zip 成员清单、工作表/合并范围/公式/格式基线。

### 5.2 每次运行应记录

TV ID/run ID、时间、候选路线、代码/环境版本、Provider 与请求/响应模型（若适用）、输入/输出文件 SHA-256、API/tool call IDs、耗时和错误类别、操作原话及脱敏摘要、前后差异清单、独立回读结果、确认问题/用户回复、附件消息关联及浏览器下载结果。禁止记录 Provider 密钥、Cookie、完整 Authorization 头或未经批准的真实业务数据。

### 6.1 数据刷新数据治理

为确定性测试，优先在隔离 Odoo 测试数据库用合成记录和当前测试用户 ACL 测试两个快照之间的变化；任何数据变更只通过 Odoo ORM，并需有独立批准和清理/回滚证明。Data Tool JSON 契约应在不依赖 Excel 模板的测试中检查记录身份、业务键、快照筛选范围/时点、记录总数与分页完整性、空值类型及权限；不得把单元格坐标或目标映射放进 Data Tool 响应。真实 Provider E2E 在数据政策未批准前仍只使用合成工作簿和合成字段值。

若进行真实业务记录验证：限定当前用户可读字段，只读检索；不得为测试篡改真实业务记录。自然数据变化无法稳定复现时，应将实时数据刷新真实 E2E 标记 `INCONCLUSIVE/BLOCKED`，不可虚构有变化的源记录。

## 7. 比较指标与路线判定

### 7.1 记录指标

- **功能覆盖**：自然语言目标完成率、未支持操作的正确识别/澄清率；按操作类别分别记录，不把有限样本当普遍能力。
- **文件质量**：目标/非目标单元格差异、公式与引用、格式/结构保留、打开/回读成功、实际下载文件一致性。
- **可靠性**：多轮状态连续性、候选/确认绑定、超时/失败恢复、重复操作/Finalize 幂等行为。
- **安全与隐私**：Provider 实际输入、Sandbox 文件/网络/资源边界、Odoo 凭据隔离、当前用户 ACL、文件访问/消息关联。
- **成本与维护**：原型开发/修改工作量、依赖/版本升级点、单轮/多轮耗时、人工复核量、回归用例数量与新操作支持成本。性能预算以冻结 SRS/M1 基线为准，不在本 TV 自行设新阈值。

### 7.2 状态定义

`PASS`：该候选在预先批准范围内满足全部该场景成功条件并有实际候选文件/回读证据。
`FAIL`：已执行并违反一项以上必须条件。
`INCONCLUSIVE`：执行了但样本/日志/差异不足以判断。
`BLOCKED`：需要的权限、数据政策、环境或 Provider 接口不具备。
`NOT RUN`：未执行。
`NOT SUPPORTED`：候选路线明确不提供该操作/结构；若能安全识别并准确告知，不能单独视为系统失败，但不代表该产品要求已满足。

Candidate A 的结果只建立现有能力对照基线，不能证明首轮后 LLM 文件编辑已实现，也不能推定 Candidate B/C 成功。Candidate B/C 是后续编辑能力候选，B 的真实 Provider 能力和 C 的原型能力须分别以实际证据判定。只有所有产品必需用例都在某路线达成门槛，才可推荐路线；即使如此仍须人工批准变更。Candidate C 原型开发/运行须有独立授权，TV 计划或设计评估本身不是授权，也不能作为原型测试证据。
