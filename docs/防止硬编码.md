# 🛡️ 防硬编码护身符 V2.0

## 一、必带前缀：最高工程纪律

【最高工程纪律：通用引擎不可腐化】

在开始任何代码修改之前，必须确认：

本项目的 `office_core` 是通用 Office 文档操作引擎，不是针对某个业务、客户或模板编写的专用脚本。

本次任务的目标是从根本上修复问题，不是绕过测试失败，也不是仅让当前案例通过。

### 强制规则

1. **禁止无通用规则依据的硬编码和业务特判。**

   不得为了修复当前问题，根据特定客户、Odoo 业务模型（如 `sale.order`）、模板名称、文件名、固定坐标（如 `B4`）、固定行号、特定公式文本或测试 fixture 内容添加专用分支。

2. **修复必须具有可解释的通用规则依据。**

   每项核心修改都必须能够回答：
   - 它修复了哪一类问题？
   - 适用于哪些输入和操作？
   - 哪些边界条件不受支持？
   - 为什么应当在当前架构层修复？
   - 为什么不应该将该逻辑放入 Mapping、Skill、调用方或测试数据？

3. **不得把禁止硬编码误解为禁止条件判断。**

   基于通用契约、类型、文档结构、安全约束或明确配置的条件判断是允许的。

   例如，拒绝包含不支持公式结构的插行操作属于合法的通用安全判断；仅因某个客户模板使用特定单元格而修改执行行为，则属于需要禁止的业务特判。

4. **优先扩展通用能力，不得绕过契约。**

   如果当前操作契约无法表达所需行为，应先分析契约是否需要扩展，而不是直接在执行器中添加私有逻辑。

   如果问题属于业务映射，应优先修复 Mapping 或 Skill；如果属于文件格式处理，应在相应 Adapter 中实现有边界的通用能力。

5. **禁止以降低验证标准换取通过。**

   不得为了通过当前测试而删除断言、跳过验证、扩大未经验证的操作范围、绕过权限或放宽安全限制。

6. **先确定根因，再修改代码。**

   根因不明确时，先检查调用链、构造最小复现测试并收集证据。不得通过连续试错在核心引擎中堆积特例。

7. **保留既有工程安全约束。**

   不修改 Odoo 官方 addon；不使用 `sudo()` 或 SQL 绕过业务权限；不执行破坏性 Git 操作；不覆盖无关用户修改；未经授权不暂存、提交或推送。

任何修改如果违反以上规则，即使全部功能测试通过，也不能视为合格交付。

## 二、必带后缀：防腐化自查与交付证据

【防腐化自查：交付前必须完成】

在提交最终报告之前，必须实际完成以下检查，并提供证据。不得仅声明“没有硬编码”或“保持通用性”。

### 1. 核心代码审查

列出本次修改的核心代码片段，并解释：

- 每个新增条件分支依据什么通用规则执行；
- 是否出现客户、业务模型、模板、文件名、固定坐标或固定公式特判；
- 是否引入业务层依赖、重复执行器或绕过统一 Validator 的路径；
- 修改是否位于正确的架构层。

不能只贴一小段有利代码而忽略其他修改文件。必须结合完整 Diff 和相关调用链审查。

### 2. 自动化测试证据

贴出新增或修改的关键测试，并说明其验证的规则。

根据修改范围，至少考虑：

- 原始失败案例；
- 使用不同数据、位置或文档结构的同类案例；
- 边界条件与不支持的输入；
- 非目标区域和受保护结构不变；
- 执行或验证失败时不得发布不合格候选文件。

对于底层通用能力，必须证明在没有 Odoo 业务模型、客户信息或特定模板名称的情况下，该能力仍然成立。

不得仅通过一个固定 fixture 的测试就声称通用性已得到证明。

### 3. 操作契约与 Schema 检查

如果本次修改涉及底层操作能力，必须明确说明：

- 是否扩展 Canonical Document Operations；
- 如果扩展，Schema 版本、操作类型、参数和语义是什么；
- 完整操作列表如何在执行前校验；
- Adapter 如何实现该操作；
- Validator 如何在保存后验证操作结果；
- 不支持的输入如何安全拒绝。

如果本次只是修复现有契约下的算法 Bug，不需要为了形式而扩展 Schema，但必须说明为什么现有契约已经足够。

### 4. 真实验证结果

列出实际执行的命令和结果，明确区分：

- 静态检查；
- 独立 Python 测试；
- 架构约束测试；
- Odoo TransactionCase；
- M2 集成测试；
- 浏览器或 Provider 端到端测试；
- 保存后独立文件回读。

未运行的测试必须明确标记为未运行，不得推断通过。

### 5. 最终判定

必须分别判断：

- 功能正确性是否通过；
- 架构通用性是否通过；
- 安全与权限边界是否通过；
- 回归测试是否充分；
- 是否仍有未验证风险。

如果功能测试通过，但发现业务特判、契约绕行或验证弱化，本次修复仍然不合格。

如果证据不足，应如实标记为未完成，而不是宣称通过。
